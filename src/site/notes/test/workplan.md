## 下篇 · 26 周路线

### 2. 6 小时怎么分（整套计划最重要的设计）

6 小时不是连续学 6 小时，而是**四种性质不同的活动各占一块**。

| 时段 | 时长 | 内容 | 硬性产出 |
| --- | --- | --- | --- |
| 上午 | 2h | **刻意练习**：算法 1 题（30 min）+ 当周主题动手写（90 min） | 1 道题 + 1 段能跑的代码 |
| 下午 | 2.5h | **项目推进**：真实项目，写代码为主 | 1 个 commit + 能演示的产物 |
| 傍晚 | 1h | **限时输入**：官方文档 / 源码 / 课程 | 3 条笔记 |
| 晚上 | 0.5h | **输出与规划**：当日笔记 + 明日任务 | 笔记 + 明日 3 件事 |

**三条纪律**

1. 6 小时里**至少 4.5 小时在动手**，限时输入不超过 1.5 小时。这条比什么都重要。
2. 每 50 分钟休息 10 分钟，不要硬撑。
3. 每天必须留下 commit。**没有 commit 的一天 = 没学。**

### 3. 项目主线：一个项目贯穿 26 周

不要做十几个小项目。**只做一个，让它逐周长大**——这样你能看见系统是怎么长出来的，而不是每次从零开始。

**项目：AI 内容助手** —— 抓取技术热点 → LLM 生成中文摘要 → 发布 / 提供服务 → 最后变成能查你笔记的问答服务。

| 阶段 | 形态 |
| --- | --- |
| W2–W6 | 命令行脚本 → 每天自动产出 Markdown 内容 |
| W7–W12 | Web 服务 → 有界面、有数据库、有用户、公网可访问 |
| W13–W18 | Java 重写后端 → 前后端分离 + 缓存 |
| W19–W22 | 接入 RAG / Agent → 能查你自己的 Obsidian 笔记 |
| W23–W26 | 架构收口 → 技术方案文档 + 简历 + 面试准备 |

### 4. 每周节奏与防崩盘机制

- 周一～周六：满负荷 6 小时
- **周日：减半（3 小时）**，下午完全断网休息
- **法定节假日当周自动减半**，不要为了「进度」硬补
- 每晚睡前 5 分钟：写明天的 3 件事

**每 6 周一次体检**（W6 / W12 / W18 / W24 的周日做），回答 5 个问题：

1. 这 6 周我一共提交了多少次 commit？
2. 有没有一个**能演示给别人看**的东西？
3. 有没有真人用过我做的东西？
4. 我能不能不看资料，把这 6 周学的东西讲清楚？
5. 我的睡眠和情绪还正常吗？

任何一条答不上来 → **下一周减半，把它补上，别硬冲**。六个月是马拉松，中途放弃是最大的失败方式，比学得慢严重得多。

### 8. 六个月里最大的六个坑

1. **前松后紧。** 26 周听起来很长，前两个月最容易松懈。用每 6 周的体检卡住。
2. **6 小时全在输入。** 看视频 6 小时，一周后什么都不会。输入硬性上限 1.5 小时。
3. **中途换方向。** 听说前端好、听说算法重要，就换赛道。**一条线走完再换。**
4. **不出门、不见人。** 每周至少找一个真人聊一次你的代码或项目。
5. **追求完美方案。** 先跑通再优化——一个能跑的丑东西，胜过一个不能跑的美方案。
6. **一遇报错就换方案。** 报错的最后一行才是你真正的老师，先读懂它。
