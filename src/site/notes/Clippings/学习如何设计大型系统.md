### Learn how to design large-scale systems学习如何设计大型系统

Learning how to design scalable systems will help you become a better engineer.  
学习如何设计可扩展的系统将有助于你成为一名更优秀的工程师。

System design is a broad topic. There are a **vast number of resources scattered throughout the web** on system design principles.  
系统设计是一个涵盖面很广的主题。 **网络上有很多关于系统设计原则的资源** 。

This repo is an **organized collection** of resources to help you learn how to build systems at scale.

## How to approach a system design interview question如何应对系统设计面试题

> How to tackle a system design interview question.  
> 如何应对系统设计面试题。

The system design interview is an **open-ended conversation**. You are expected to lead it.  
系统设计面试是一场 **开放式的对话** ，你需要主导对话。

You can use the following steps to guide the discussion. To help solidify this process, work through the [System design interview questions with solutions](#system-design-interview-questions-with-solutions) section using the following steps.  
您可以按照以下步骤引导讨论。为了帮助您巩固这一过程，请按照以下步骤完成 [系统设计面试题及解答](#system-design-interview-questions-with-solutions) 部分。

### Step 1: Outline use cases, constraints, and assumptions第一步：概述用例、约束条件和假设

Gather requirements and scope the problem. Ask questions to clarify use cases and constraints. Discuss assumptions.  
收集需求并确定问题范围。提出问题以明确使用场景和限制条件。讨论假设。

- Who is going to use it?  
	谁会使用它？
- How are they going to use it?  
	他们打算如何使用它？
- How many users are there?  
	有多少用户？
- What does the system do?  
	这个系统是做什么的？
- What are the inputs and outputs of the system?  
	该系统的输入和输出是什么？
- How much data do we expect to handle?  
	我们预计会处理多少数据？
- How many requests per second do we expect?  
	我们预计每秒会有多少个请求？
- What is the expected read to write ratio?  
	预期的读写比是多少？

### Step 2: Create a high level design步骤二：创建高层设计

Outline a high level design with all important components.  
概述包含所有重要组成部分的高级设计方案。

- Sketch the main components and connections  
	绘制主要部件和连接示意图
- Justify your ideas  
	请阐述你的观点。

### Step 3: Design core components步骤 3：设计核心组件

## Performance vs scalability性能与可扩展性

A service is **scalable** if it results in increased **performance** in a manner proportional to resources added. Generally, increasing performance means serving more units of work, but it can also be to handle larger units of work, such as when datasets grow.<sup><a href="http://www.allthingsdistributed.com/2006/03/a_word_on_scalability.html">1</a></sup>  
如果一项服务能够以与资源增加成比例的方式提升 **性能** ，则称该服务具有 **可扩展性** 。通常，提升性能意味着处理更多的工作单元，但也可能意味着处理更大的工作单元，例如当数据集增长时。 <sup><a href="http://www.allthingsdistributed.com/2006/03/a_word_on_scalability.html">1</a></sup>

Another way to look at performance vs scalability:  
换个角度来看性能与可扩展性：

- If you have a **performance** problem, your system is slow for a single user.  
	如果出现 **性能** 问题，则表示您的系统对于单个用户来说运行缓慢。
- If you have a **scalability** problem, your system is fast for a single user but slow under heavy load.  
	如果你的系统存在 **可扩展性** 问题，那么在单个用户使用时速度很快，但在高负载下速度会变慢。

## Availability vs consistency

### CAP theorem

[![](https://github.com/donnemartin/system-design-primer/raw/master/images/bgLMI2u.png)](https://github.com/donnemartin/system-design-primer/blob/master/images/bgLMI2u.png)  
*[Source: CAP theorem revisited](https://robertgreiner.com/cap-theorem-revisited)*

In a distributed computer system, you can only support two of the following guarantees:

- **Consistency** - Every read receives the most recent write or an error
- **Availability** - Every request receives a response, without guarantee that it contains the most recent version of the information
- **Partition Tolerance** - The system continues to operate despite arbitrary partitioning due to network failures

*Networks aren't reliable, so you'll need to support partition tolerance. You'll need to make a software tradeoff between consistency and availability.*

#### CP - consistency and partition tolerance

Waiting for a response from the partitioned node might result in a timeout error. CP is a good choice if your business needs require atomic reads and writes.

#### AP - availability and partition tolerance

Responses return the most readily available version of the data available on any node, which might not be the latest. Writes might take some time to propagate when the partition is resolved.

AP is a good choice if the business needs to allow for [eventual consistency](#eventual-consistency) or when the system needs to continue working despite external errors.

## Consistency patterns一致性模式

With multiple copies of the same data, we are faced with options on how to synchronize them so clients have a consistent view of the data. Recall the definition of consistency from the [CAP theorem](#cap-theorem) - Every read receives the most recent write or an error.  
当存在同一数据的多个副本时，我们需要选择几种同步方式，以确保客户端能够获得一致的数据视图。回顾一下 [CAP 定理](#cap-theorem) 中对一致性的定义——每次读取操作要么接收到最近一次写入的数据，要么接收到错误信息。

### Weak consistency一致性较弱

After a write, reads may or may not see it. A best effort approach is taken.  
写入操作完成后，读取操作可能看到该数据，也可能看不到。系统会尽力而为。

---

This approach is seen in systems such as memcached. Weak consistency works well in real time use cases such as VoIP, video chat, and realtime multiplayer games.  
这种方法常见于 memcached 等系统中。弱一致性在 VoIP、视频聊天和实时多人游戏等实时应用场景中表现良好。  
For example, if you are on a phone call and lose reception for a few seconds, when you regain connection you do not hear what was spoken during connection loss.  
例如，如果您正在打电话，但信号中断了几秒钟，当您恢复连接时，您将听不到在信号中断期间说的话。

---

### Eventual consistency最终一致性

After a write, reads will eventually see it (typically within milliseconds). Data is replicated asynchronously.  
写入操作完成后，读取操作最终会检测到数据（通常在几毫秒内）。数据以异步方式复制。

This approach is seen in systems such as DNS and email. Eventual consistency works well in highly available systems.  
这种方法常见于 DNS 和电子邮件等系统中。最终一致性在高可用性系统中效果显著。

### Strong consistency高度一致性

After a write, reads will see it. Data is replicated synchronously.  
写入操作完成后，读取操作即可看到更新。数据以同步方式复制。

This approach is seen in file systems and RDBMSes. Strong consistency works well in systems that need transactions.  
这种方法常见于文件系统和关系数据库管理系统（RDBMS）。强一致性在需要事务处理的系统中效果显著。

## Availability patterns

There are two complementary patterns to support high availability: **fail-over** and **replication**.

### Fail-over

#### Active-passive

With active-passive fail-over, heartbeats are sent between the active and the passive server on standby. If the heartbeat is interrupted, the passive server takes over the active's IP address and resumes service.

The length of downtime is determined by whether the passive server is already running in 'hot' standby or whether it needs to start up from 'cold' standby. Only the active server handles traffic.

Active-passive failover can also be referred to as master-slave failover.

#### Active-active

In active-active, both servers are managing traffic, spreading the load between them.

If the servers are public-facing, the DNS would need to know about the public IPs of both servers. If the servers are internal-facing, application logic would need to know about both servers.

Active-active failover can also be referred to as master-master failover.

### Disadvantage(s): failover

- Fail-over adds more hardware and additional complexity.
- There is a potential for loss of data if the active system fails before any newly written data can be replicated to the passive.

可用性通常以正常运行时间（或停机时间）占服务可用时间的百分比来量化。可用性通常用 9 的个数来衡量——可用性为 99.99% 的服务被描述为有四个 9。

#### Availability in parallel vs in sequence并行可用性与顺序可用性

If a service consists of multiple components prone to failure, the service's overall availability depends on whether the components are in sequence or in parallel.  
如果一项服务由多个容易发生故障的组件构成，则该服务的整体可用性取决于这些组件是按顺序运行还是并行运行。

###### In sequence按顺序

Overall availability decreases when two components with availability < 100% are in sequence:  
当两个可用性低于 100% 的组件串联在一起时，整体可用性会下降：

```
Availability (Total) = Availability (Foo) * Availability (Bar)
```

If both `Foo` and `Bar` each had 99.9% availability, their total availability in sequence would be 99.8%.

###### In parallel

Overall availability increases when two components with availability < 100% are in parallel:

```
Availability (Total) = 1 - (1 - Availability (Foo)) * (1 - Availability (Bar))
```

If both `Foo` and `Bar` each had 99.9% availability, their total availability in parallel would be 99.9999%.

## Domain name system

[![](https://github.com/donnemartin/system-design-primer/raw/master/images/IOyLj4i.jpg)](https://github.com/donnemartin/system-design-primer/blob/master/images/IOyLj4i.jpg)  
*[Source: DNS security presentation  
来源：DNS 安全演示文稿](http://www.slideshare.net/srikrupa5/dns-security-presentation-issa)*

A Domain Name System (DNS) translates a domain name such as [www.example.com](http://www.example.com/) to an IP address.  
域名系统（DNS）将域名（例如 [www.example.com](http://www.example.com/) ）转换为 IP 地址。

---

DNS is hierarchical, with a few authoritative servers at the top level. Your router or ISP provides information about which DNS server(s) to contact when doing a lookup. Lower level DNS servers cache mappings, which could become stale due to DNS propagation delays.  
DNS 是分层结构的，顶层有少数权威服务器。您的路由器或 ISP 会提供信息，告诉您在进行 DNS 查询时应该联系哪个或哪些 DNS 服务器。较低级别的 DNS 服务器会缓存映射关系，但由于 DNS 传播延迟，这些映射关系可能会过时。  
DNS results can also be cached by your browser or OS for a certain period of time, determined by the [time to live (TTL)](https://en.wikipedia.org/wiki/Time_to_live).  
DNS 查询结果也可以被浏览器或操作系统缓存一段时间，具体时间由 [生存时间 (TTL)](https://en.wikipedia.org/wiki/Time_to_live) 决定。

---

- **NS record (name server)** - Specifies the DNS servers for your domain/subdomain.  
	**NS 记录（名称服务器）** - 指定您的域/子域的 DNS 服务器。
- **MX record (mail exchange)** - Specifies the mail servers for accepting messages.  
	**MX 记录（邮件交换）** - 指定用于接收邮件的邮件服务器。
- **A record (address)** - Points a name to an IP address.  
	**记录（地址）** ——将名称指向 IP 地址。
- **CNAME (canonical)** - Points a name to another name or `CNAME` (example.com to [www.example.com](http://www.example.com/)) or to an `A` record.  
	**CNAME（规范）** - 将一个名称指向另一个名称或 `CNAME` （例如 example.com 指向 [www.example.com](http://www.example.com/) ）或 `A` 记录。

Services such as [CloudFlare](https://www.cloudflare.com/dns/) and [Route 53](https://aws.amazon.com/route53/) provide managed DNS services. Some DNS services can route traffic through various methods:  
[CloudFlare](https://www.cloudflare.com/dns/) 和 [Route 53](https://aws.amazon.com/route53/) 等服务提供托管 DNS 服务。一些 DNS 服务可以通过多种方式路由流量：

- [Weighted round robin  
	加权循环赛](https://www.jscape.com/blog/load-balancing-algorithms)
	- Prevent traffic from going to servers under maintenance  
		防止流量流向正在维护的服务器
		- Balance between varying cluster sizes  
		不同集群规模之间的平衡
		- A/B testing  
		A/B 测试
- [Latency-based  
	基于延迟](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-latency.html)
- [Geolocation-based  
	基于地理位置](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-geo.html)

### Disadvantage(s): DNS缺点：DNS

- Accessing a DNS server introduces a slight delay, although mitigated by caching described above.  
	访问 DNS 服务器会引入轻微延迟，但可以通过上述缓存机制来缓解。
- DNS server management could be complex and is generally managed by [governments, ISPs, and large companies](http://superuser.com/questions/472695/who-controls-the-dns-servers/472729).  
	DNS 服务器管理可能很复杂，通常由 [政府、互联网服务提供商和大型公司](http://superuser.com/questions/472695/who-controls-the-dns-servers/472729) 管理。
- DNS services have recently come under [DDoS attack](http://dyn.com/blog/dyn-analysis-summary-of-friday-october-21-attack/), preventing users from accessing websites such as Twitter without knowing Twitter's IP address(es).  
	DNS 服务最近遭受了 [DDoS 攻击](http://dyn.com/blog/dyn-analysis-summary-of-friday-october-21-attack/) ，导致用户在不知道 Twitter 的 IP 地址的情况下无法访问 Twitter 等网站。

## Content delivery network内容分发网络

[![](https://github.com/donnemartin/system-design-primer/raw/master/images/h9TAuGI.jpg)](https://github.com/donnemartin/system-design-primer/blob/master/images/h9TAuGI.jpg)  
*[Source: Why use a CDN  
来源：为什么要使用 CDN](https://www.creative-artworks.eu/why-use-a-content-delivery-network-cdn/)*

---

A content delivery network (CDN) is a globally distributed network of proxy servers, serving content from locations closer to the user.  
内容分发网络 (CDN) 是一个全球分布式的代理服务器网络，从距离用户更近的位置提供内容。  
Generally, static files such as HTML/CSS/JS, photos, and videos are served from CDN, although some CDNs such as Amazon's CloudFront support dynamic content. The site's DNS resolution will tell clients which server to contact.  
通常情况下，静态文件（例如 HTML/CSS/JS、图片和视频）由 CDN 提供，不过也有一些 CDN（例如亚马逊的 CloudFront）支持动态内容。网站的 DNS 解析会告诉客户端应该联系哪个服务器。

---

Serving content from CDNs can significantly improve performance in two ways:  
通过 CDN 提供内容可以从两个方面显著提高性能：

- Users receive content from data centers close to them  
	用户从离他们较近的数据中心接收内容。
- Your servers do not have to serve requests that the CDN fulfills  
	您的服务器无需处理由 CDN 处理的请求。

### Push CDNs推送 CDN

---

Push CDNs receive new content whenever changes occur on your server. You take full responsibility for providing content, uploading directly to the CDN and rewriting URLs to point to the CDN. You can configure when content expires and when it is updated.  
推送式 CDN 会在您的服务器上发生更改时接收新内容。您需要全权负责提供内容、直接上传到 CDN 以及重写 URL 以指向 CDN。您可以配置内容的过期时间和更新时间。  
Content is uploaded only when it is new or changed, minimizing traffic, but maximizing storage.  
内容仅在新增或更改时上传，从而最大限度地减少流量，同时最大限度地利用存储空间。

---

Sites with a small amount of traffic or sites with content that isn't often updated work well with push CDNs. Content is placed on the CDNs once, instead of being re-pulled at regular intervals.  
流量较小或内容更新频率不高的网站非常适合使用推送式 CDN。内容只需在 CDN 上放置一次，无需定期重新拉取。

### Pull CDNs拉取 CDN

Pull CDNs grab new content from your server when the first user requests the content. You leave the content on your server and rewrite URLs to point to the CDN. This results in a slower request until the content is cached on the CDN.  
拉取式 CDN 会在第一个用户请求内容时从您的服务器获取新内容。您将内容保留在服务器上，并将 URL 重写为指向 CDN。这会导致请求速度变慢，直到内容缓存到 CDN 上为止。

A [time-to-live (TTL)](https://en.wikipedia.org/wiki/Time_to_live) determines how long content is cached. Pull CDNs minimize storage space on the CDN, but can create redundant traffic if files expire and are pulled before they have actually changed.  
[生存时间 (TTL)](https://en.wikipedia.org/wiki/Time_to_live) 决定了内容缓存的时长。拉取式 CDN 可以最大限度地减少 CDN 上的存储空间，但如果文件过期并在实际更改之前被拉取，则可能会造成冗余流量。

Sites with heavy traffic work well with pull CDNs, as traffic is spread out more evenly with only recently-requested content remaining on the CDN.  
流量大的网站非常适合使用拉取式 CDN，因为流量会更均匀地分散，CDN 上只会保留最近请求的内容。

### Disadvantage(s): CDN缺点：CDN

- CDN costs could be significant depending on traffic, although this should be weighed with additional costs you would incur not using a CDN.  
	CDN 的费用可能很大，具体取决于流量，不过这应该与不使用 CDN 而产生的额外费用进行权衡。
- Content might be stale if it is updated before the TTL expires it.  
	如果内容在 TTL 过期之前更新，则内容可能已过时。
- CDNs require changing URLs for static content to point to the CDN.  
	CDN 需要更改静态内容的 URL，使其指向 CDN。

## Load balancer负载均衡器

[![](https://github.com/donnemartin/system-design-primer/raw/master/images/h81n9iK.png)](https://github.com/donnemartin/system-design-primer/blob/master/images/h81n9iK.png)  
*[Source: Scalable system design patterns  
来源：可扩展系统设计模式](http://horicky.blogspot.com/2010/10/scalable-system-design-patterns.html)*

Load balancers distribute incoming client requests to computing resources such as application servers and databases. In each case, the load balancer returns the response from the computing resource to the appropriate client. Load balancers are effective at:  
负载均衡器将传入的客户端请求分发到计算资源，例如应用服务器和数据库。在每个应用中，负载均衡器都会将计算资源的响应返回给相应的客户端。负载均衡器的优势在于：

- Preventing requests from going to unhealthy servers  
	防止请求发送到不健康的服务器
- Preventing overloading resources  
	防止资源过载
- Helping to eliminate a single point of failure  
	有助于消除单点故障

Load balancers can be implemented with hardware (expensive) or with software such as HAProxy.  
负载均衡器可以通过硬件（成本较高）或软件（例如 HAProxy）来实现。

Additional benefits include:  
其他福利包括：

- **SSL termination** - Decrypt incoming requests and encrypt server responses so backend servers do not have to perform these potentially expensive operations  
	**SSL 终止** - 解密传入请求并加密服务器响应，从而避免后端服务器执行这些可能代价高昂的操作。
	- Removes the need to install [X.509 certificates](https://en.wikipedia.org/wiki/X.509) on each server  
		无需在每台服务器上安装 [X.509 证书](https://en.wikipedia.org/wiki/X.509)
- **Session persistence** - Issue cookies and route a specific client's requests to same instance if the web apps do not keep track of sessions  
	**会话持久性** - 如果 Web 应用程序不跟踪会话，则颁发 cookie 并将特定客户端的请求路由到同一实例。

To protect against failures, it's common to set up multiple load balancers, either in [active-passive](#active-passive) or [active-active](#active-active) mode.  
为了防止故障，通常会设置多个负载均衡器，采用 [主备](#active-passive) 模式或 [主主](#active-active) 模式。

Load balancers can route traffic based on various metrics, including:  
负载均衡器可以根据各种指标来路由流量，包括：

- Random  
	随机的
- Least loaded  
	负载最少
- Session/cookies  
	会话/cookie
- [Round robin or weighted round robin  
	循环赛或加权循环赛](https://www.g33kinfo.com/info/round-robin-vs-weighted-round-robin-lb)
- [Layer 4  
	第四层](#layer-4-load-balancing)
- [Layer 7  
	第七层](#layer-7-load-balancing)

### Layer 4 load balancing第四层负载均衡

Layer 4 load balancers look at info at the [transport layer](#communication) to decide how to distribute requests. Generally, this involves the source, destination IP addresses, and ports in the header, but not the contents of the packet. Layer 4 load balancers forward network packets to and from the upstream server, performing [Network Address Translation (NAT)](https://web.archive.org/web/20240117134735/https://www.nginx.com/resources/glossary/layer-4-load-balancing/).  
第四层负载均衡器会查看 [传输层](#communication) 的信息来决定如何分配请求。通常，这包括数据包头部中的源 IP 地址、目标 IP 地址和端口，但不包括数据包的内容。第四层负载均衡器会将网络数据包转发到上游服务器并从上游服务器接收数据包，执行 [网络地址转换 (NAT)](https://web.archive.org/web/20240117134735/https://www.nginx.com/resources/glossary/layer-4-load-balancing/) 。

### Layer 7 load balancing第七层负载均衡

---

Layer 7 load balancers look at the [application layer](#communication) to decide how to distribute requests. This can involve contents of the header, message, and cookies. Layer 7 load balancers terminate network traffic, reads the message, makes a load-balancing decision, then opens a connection to the selected server.  
第七层负载均衡器会查看 [应用层](#communication) ，以决定如何分配请求。这可能涉及请求头、消息和 Cookie 的内容。第七层负载均衡器会终止网络流量，读取消息，做出负载均衡决策，然后与选定的服务器建立连接。  
For example, a layer 7 load balancer can direct video traffic to servers that host videos while directing more sensitive user billing traffic to security-hardened servers.  
例如，第 7 层负载均衡器可以将视频流量定向到托管视频的服务器，同时将更敏感的用户计费流量定向到安全加固的服务器。

---

At the cost of flexibility, layer 4 load balancing requires less time and computing resources than Layer 7, although the performance impact can be minimal on modern commodity hardware.  
虽然牺牲了灵活性，但第 4 层负载均衡所需的时间和计算资源比第 7 层少，尽管在现代通用硬件上性能影响可能很小。

### Horizontal scaling水平缩放

Load balancers can also help with horizontal scaling, improving performance and availability. Scaling out using commodity machines is more cost efficient and results in higher availability than scaling up a single server on more expensive hardware, called **Vertical Scaling**. It is also easier to hire for talent working on commodity hardware than it is for specialized enterprise systems.  
负载均衡器还可以帮助实现横向扩展，从而提升性能和可用性。使用通用机器进行横向扩展比在更昂贵的硬件上扩展单个服务器（称为 **纵向扩展** ）更具成本效益，并且可用性更高。此外，与专用企业系统相比，为通用硬件招聘人才也更容易。

#### Disadvantage(s): horizontal scaling缺点：横向缩放

- Scaling horizontally introduces complexity and involves cloning servers  
	水平扩展会引入复杂性，并且涉及服务器克隆。
	- Servers should be stateless: they should not contain any user-related data like sessions or profile pictures  
		服务器应该是无状态的：它们不应该包含任何与用户相关的数据，例如会话或个人资料图片。
		- Sessions can be stored in a centralized data store such as a [database](#database) (SQL, NoSQL) or a persistent [cache](#cache) (Redis, Memcached)  
		会话可以存储在集中式数据存储中，例如 [数据库](#database) （SQL、NoSQL）或持久 [缓存](#cache) （Redis、Memcached）。
- Downstream servers such as caches and databases need to handle more simultaneous connections as upstream servers scale out  
	随着上游服务器横向扩展，下游服务器（例如缓存和数据库）需要处理更多并发连接。

### Disadvantage(s): load balancer缺点：负载均衡器

- The load balancer can become a performance bottleneck if it does not have enough resources or if it is not configured properly.  
	如果负载均衡器资源不足或配置不当，则可能成为性能瓶颈。
- Introducing a load balancer to help eliminate a single point of failure results in increased complexity.  
	引入负载均衡器来帮助消除单点故障会导致复杂性增加。
- A single load balancer is a single point of failure, configuring multiple load balancers further increases complexity.  
	单个负载均衡器是单点故障，配置多个负载均衡器会进一步增加复杂性。

## Reverse proxy (web server)反向代理（Web 服务器）

[![](https://github.com/donnemartin/system-design-primer/raw/master/images/n41Azff.png)](https://github.com/donnemartin/system-design-primer/blob/master/images/n41Azff.png)  
*[Source: Wikipedia  
来源：维基百科](https://upload.wikimedia.org/wikipedia/commons/6/67/Reverse_proxy_h2g2bob.svg)*

A reverse proxy is a web server that centralizes internal services and provides unified interfaces to the public. Requests from clients are forwarded to a server that can fulfill it before the reverse proxy returns the server's response to the client.  
反向代理是一种网络服务器，它集中管理内部服务，并向公众提供统一的接口。客户端的请求会被转发到能够满足请求的服务器，然后反向代理再将服务器的响应返回给客户端。

Additional benefits include:  
其他福利包括：

- **Increased security** - Hide information about backend servers, blacklist IPs, limit number of connections per client  
	**增强安全性** - 隐藏后端服务器信息、将 IP 地址列入黑名单、限制每个客户端的连接数
- **Increased scalability and flexibility** - Clients only see the reverse proxy's IP, allowing you to scale servers or change their configuration  
	**更高的可扩展性和灵活性** ——客户端只能看到反向代理的 IP 地址，因此您可以扩展服务器或更改其配置。
- **SSL termination** - Decrypt incoming requests and encrypt server responses so backend servers do not have to perform these potentially expensive operations  
	**SSL 终止** - 解密传入请求并加密服务器响应，从而避免后端服务器执行这些可能代价高昂的操作。
	- Removes the need to install [X.509 certificates](https://en.wikipedia.org/wiki/X.509) on each server  
		无需在每台服务器上安装 [X.509 证书](https://en.wikipedia.org/wiki/X.509)
- **Compression** - Compress server responses  
	**压缩** - 压缩服务器响应
- **Caching** - Return the response for cached requests  
	**缓存** - 返回已缓存请求的响应
- **Static content** - Serve static content directly  
	**静态内容** - 直接提供静态内容
	- HTML/CSS/JS
		- Photos  
		照片
		- Videos  
		视频
		- Etc

### Load balancer vs reverse proxy负载均衡器与反向代理

- Deploying a load balancer is useful when you have multiple servers. Often, load balancers route traffic to a set of servers serving the same function.  
	当您有多台服务器时，部署负载均衡器非常有用。通常，负载均衡器会将流量路由到一组执行相同功能的服务器。
- Reverse proxies can be useful even with just one web server or application server, opening up the benefits described in the previous section.  
	即使只有一个 Web 服务器或应用程序服务器，反向代理也很有用，可以带来上一节中描述的好处。
- Solutions such as NGINX and HAProxy can support both layer 7 reverse proxying and load balancing.  
	NGINX 和 HAProxy 等解决方案可以同时支持第 7 层反向代理和负载均衡。

### Disadvantage(s): reverse proxy缺点：反向代理

- Introducing a reverse proxy results in increased complexity.  
	引入反向代理会导致复杂性增加。
- A single reverse proxy is a single point of failure, configuring multiple reverse proxies (ie a [failover](https://en.wikipedia.org/wiki/Failover)) further increases complexity.  
	单个反向代理是单点故障，配置多个反向代理（即 [故障转移](https://en.wikipedia.org/wiki/Failover) ）会进一步增加复杂性。

## Application layer应用层

[![](https://github.com/donnemartin/system-design-primer/raw/master/images/yB5SYwm.png)](https://github.com/donnemartin/system-design-primer/blob/master/images/yB5SYwm.png)  
*[Source: Intro to architecting systems for scale  
来源：《可扩展系统架构入门》](http://lethain.com/introduction-to-architecting-systems-for-scale/#platform_layer)*

Separating out the web layer from the application layer (also known as platform layer) allows you to scale and configure both layers independently. Adding a new API results in adding application servers without necessarily adding additional web servers. The **single responsibility principle** advocates for small and autonomous services that work together. Small teams with small services can plan more aggressively for rapid growth.  
将 Web 层与应用层（也称为平台层）分离，可以让你独立地扩展和配置这两层。添加新的 API 只需要添加应用服务器，而无需添加额外的 Web 服务器。 **单一职责原则** 提倡创建小型且相互独立的服务，让它们协同工作。小型团队和小型服务可以更积极地规划，以应对快速增长。

Workers in the application layer also help enable [asynchronism](#asynchronism).  
应用层中的工作线程也有助于实现 [异步操作](#asynchronism) 。

### Microservices微服务

Related to this discussion are [microservices](https://en.wikipedia.org/wiki/Microservices), which can be described as a suite of independently deployable, small, modular services. Each service runs a unique process and communicates through a well-defined, lightweight mechanism to serve a business goal. <sup><a href="https://smartbear.com/learn/api-design/what-are-microservices">1</a></sup>  
与此讨论相关的是 [微服务](https://en.wikipedia.org/wiki/Microservices) ，它可以被描述为一套可独立部署的小型模块化服务。每个服务运行一个独特的进程，并通过定义完善的轻量级机制进行通信，以实现业务目标。

Pinterest, for example, could have the following microservices: user profile, follower, feed, search, photo upload, etc.  
例如，Pinterest 可以包含以下微服务：用户个人资料、关注者、动态、搜索、照片上传等。

### Service Discovery服务发现

Systems such as [Consul](https://www.consul.io/docs/index.html), [Etcd](https://coreos.com/etcd/docs/latest), and [Zookeeper](http://www.slideshare.net/sauravhaloi/introduction-to-apache-zookeeper) can help services find each other by keeping track of registered names, addresses, and ports. [Health checks](https://www.consul.io/intro/getting-started/checks.html) help verify service integrity and are often done using an [HTTP](#hypertext-transfer-protocol-http) endpoint. Both Consul and Etcd have a built in [key-value store](#key-value-store) that can be useful for storing config values and other shared data.  
[Consul](https://www.consul.io/docs/index.html) 、 [Etcd](https://coreos.com/etcd/docs/latest) 和 [Zookeeper](http://www.slideshare.net/sauravhaloi/introduction-to-apache-zookeeper) 等系统可以通过跟踪已注册的名称、地址和端口来帮助服务相互发现。 [健康检查](https://www.consul.io/intro/getting-started/checks.html) 有助于验证服务的完整性，通常使用 [HTTP](#hypertext-transfer-protocol-http) 端点来完成。Consul 和 Etcd 都内置了 [键值存储](#key-value-store) ，可用于存储配置值和其他共享数据。

### Disadvantage(s): application layer缺点：应用层

- Adding an application layer with loosely coupled services requires a different approach from an architectural, operations, and process viewpoint (vs a monolithic system).  
	从架构、操作和流程的角度来看，添加具有松耦合服务的应用层需要采用不同的方法（与单体系统相比）。
- Microservices can add complexity in terms of deployments and operations.  
	微服务会增加部署和运维的复杂性。

[![](https://github.com/donnemartin/system-design-primer/raw/master/images/Xkm5CXz.png)](https://github.com/donnemartin/system-design-primer/blob/master/images/Xkm5CXz.png)

### Relational database management system (RDBMS)关系数据库管理系统（RDBMS）

A relational database like SQL is a collection of data items organized in tables.  
像 SQL 这样的关系型数据库，是由组织在表格中的数据项组成的集合。

**ACID** is a set of properties of relational database [transactions](https://en.wikipedia.org/wiki/Database_transaction).  
**ACID** 是关系数据库 [事务](https://en.wikipedia.org/wiki/Database_transaction) 的一组属性。

- **Atomicity** - Each transaction is all or nothing  
	**原子性** ——每笔交易要么全部成功，要么全部失败。
- **Consistency** - Any transaction will bring the database from one valid state to another  
	**一致性** ——任何事务都会将数据库从一个有效状态带到另一个有效状态。
- **Isolation** - Executing transactions concurrently has the same results as if the transactions were executed serially  
	**隔离性** ——并发执行事务与串行执行事务的结果相同。
- **Durability** - Once a transaction has been committed, it will remain so  
	**持久性** ——一旦交易被确认，它将一直有效。

There are many techniques to scale a relational database: **master-slave replication**, **master-master replication**, **federation**, **sharding**, **denormalization**, and **SQL tuning**.  
扩展关系数据库有很多技术： **主从复制** 、 **主主复制** 、 **联合** 、 **分片** 、 **反规范化** 和 **SQL 调优** 。

#### Master-slave replication主从复制

---

The master serves reads and writes, replicating writes to one or more slaves, which serve only reads. Slaves can also replicate to additional slaves in a tree-like fashion.  
主服务器负责读写操作，并将写入操作复制到一个或多个从服务器，从服务器仅负责读取操作。从服务器也可以以树状结构将数据复制到其他从服务器。  
If the master goes offline, the system can continue to operate in read-only mode until a slave is promoted to a master or a new master is provisioned.  
如果主节点离线，系统可以继续以只读模式运行，直到从节点被提升为主节点或配置新的主节点为止。

---

[![](https://github.com/donnemartin/system-design-primer/raw/master/images/C9ioGtn.png)](https://github.com/donnemartin/system-design-primer/blob/master/images/C9ioGtn.png)  
*[Source: Scalability, availability, stability, patterns  
来源：可扩展性、可用性、稳定性、模式](http://www.slideshare.net/jboner/scalability-availability-stability-patterns/)*

##### Disadvantage(s): master-slave replication缺点：主从复制

- Additional logic is needed to promote a slave to a master.  
	需要额外的逻辑才能将从属设备提升为主设备。
- See [Disadvantage(s): replication](#disadvantages-replication) for points related to **both** master-slave and master-master.  
	请参阅 [“缺点”部分，](#disadvantages-replication) 了解 **与** 主从模式和主主模式相关的复制问题。

#### Master-master replication主主复制

Both masters serve reads and writes and coordinate with each other on writes. If either master goes down, the system can continue to operate with both reads and writes.  
两个主服务器都负责读写操作，并且在写入操作时相互协调。如果其中一个主服务器发生故障，系统仍然可以继续进行读写操作。

[![](https://github.com/donnemartin/system-design-primer/raw/master/images/krAHLGg.png)](https://github.com/donnemartin/system-design-primer/blob/master/images/krAHLGg.png)  
*[Source: Scalability, availability, stability, patterns  
来源：可扩展性、可用性、稳定性、模式](http://www.slideshare.net/jboner/scalability-availability-stability-patterns/)*

##### Disadvantage(s): master-master replication缺点：主主复制

- You'll need a load balancer or you'll need to make changes to your application logic to determine where to write.  
	您要么需要一个负载均衡器，要么需要修改应用程序逻辑以确定写入位置。
- Most master-master systems are either loosely consistent (violating ACID) or have increased write latency due to synchronization.  
	大多数主主系统要么一致性较差（违反 ACID 原则），要么由于同步而导致写入延迟增加。
- Conflict resolution comes more into play as more write nodes are added and as latency increases.  
	随着写入节点数量的增加和延迟的增加，冲突解决机制的作用会越来越大。
- See [Disadvantage(s): replication](#disadvantages-replication) for points related to **both** master-slave and master-master.  
	请参阅 [“缺点”部分，](#disadvantages-replication) 了解 **与** 主从模式和主主模式相关的复制问题。

##### Disadvantage(s): replication缺点：复制

- There is a potential for loss of data if the master fails before any newly written data can be replicated to other nodes.  
	如果主节点在新写入的数据复制到其他节点之前发生故障，则有可能丢失数据。
- Writes are replayed to the read replicas. If there are a lot of writes, the read replicas can get bogged down with replaying writes and can't do as many reads.  
	写入操作会被重放到只读副本上。如果写入操作过多，只读副本可能会因为重放写入操作而变得不堪重负，从而导致读取操作减少。
- The more read slaves, the more you have to replicate, which leads to greater replication lag.  
	读取从节点越多，需要复制的数据就越多，这会导致更大的复制延迟。
- On some systems, writing to the master can spawn multiple threads to write in parallel, whereas read replicas only support writing sequentially with a single thread.  
	在某些系统中，向主服务器写入数据可以生成多个线程进行并行写入，而只读副本仅支持使用单个线程进行顺序写入。
- Replication adds more hardware and additional complexity.  
	复制操作会增加更多硬件和复杂性。

#### Federation联邦

[![](https://github.com/donnemartin/system-design-primer/raw/master/images/U3qV33e.png)](https://github.com/donnemartin/system-design-primer/blob/master/images/U3qV33e.png)  
*[Source: Scaling up to your first 10 million users  
来源：如何扩展到您的第一个 1000 万用户](https://www.youtube.com/watch?v=kKjm4ehYiMs)*

---

Federation (or functional partitioning) splits up databases by function. For example, instead of a single, monolithic database, you could have three databases: **forums**, **users**, and **products**, resulting in less read and write traffic to each database and therefore less replication lag. Smaller databases result in more data that can fit in memory, which in turn results in more cache hits due to improved cache locality.  
联合（或功能分区）按功能拆分数据库。例如，与其使用单一的单体数据库，不如使用三个数据库： **论坛** 、 **用户** 和 **产品** ，这样可以减少每个数据库的读写流量，从而降低复制延迟。更小的数据库意味着更多的数据可以加载到内存中，进而由于缓存局部性的提高而增加缓存命中率。  
With no single central master serializing writes you can write in parallel, increasing throughput.  
由于没有单个中央主控程序进行串行写入，您可以并行写入，从而提高吞吐量。

---

##### Disadvantage(s): federation缺点：联邦制

- Federation is not effective if your schema requires huge functions or tables.  
	如果你的模式需要庞大的函数或表，联合身份验证就无法有效发挥作用。
- You'll need to update your application logic to determine which database to read and write.  
	您需要更新应用程序逻辑，以确定要读取和写入哪个数据库。
- Joining data from two databases is more complex with a [server link](http://stackoverflow.com/questions/5145637/querying-data-by-joining-two-tables-in-two-database-on-different-servers).  
	通过 [服务器连接](http://stackoverflow.com/questions/5145637/querying-data-by-joining-two-tables-in-two-database-on-different-servers) 连接两个数据库中的数据会更加复杂。
- Federation adds more hardware and additional complexity.  
	联邦制增加了更多硬件和复杂性。

#### Sharding分片

[![](https://github.com/donnemartin/system-design-primer/raw/master/images/wU8x5Id.png)](https://github.com/donnemartin/system-design-primer/blob/master/images/wU8x5Id.png)  
*[Source: Scalability, availability, stability, patterns  
来源：可扩展性、可用性、稳定性、模式](http://www.slideshare.net/jboner/scalability-availability-stability-patterns/)*

Sharding distributes data across different databases such that each database can only manage a subset of the data. Taking a users database as an example, as the number of users increases, more shards are added to the cluster.  
分片技术将数据分布在不同的数据库中，使得每个数据库只能管理一部分数据。以用户数据库为例，随着用户数量的增加，集群中会添加更多的分片。

---

Similar to the advantages of [federation](#federation), sharding results in less read and write traffic, less replication, and more cache hits. Index size is also reduced, which generally improves performance with faster queries.  
与 [联邦](#federation) 的优势类似，分片可以减少读写流量、减少数据复制，并提高缓存命中率。索引大小也会减小，这通常可以提高性能，加快查询速度。  
If one shard goes down, the other shards are still operational, although you'll want to add some form of replication to avoid data loss. Like federation, there is no single central master serializing writes, allowing you to write in parallel with increased throughput.  
如果一个分片宕机，其他分片仍然可以正常运行，但为了避免数据丢失，最好添加某种形式的数据复制机制。与联邦机制类似，这种架构没有单一的中央主节点来串行执行写入操作，因此可以并行写入，从而提高吞吐量。

---

Common ways to shard a table of users is either through the user's last name initial or the user's geographic location.  
对用户表进行分片的常见方法是按用户姓氏的首字母或用户的地理位置进行分片。

##### Disadvantage(s): sharding缺点：分片

- You'll need to update your application logic to work with shards, which could result in complex SQL queries.  
	您需要更新应用程序逻辑以使用分片，这可能会导致复杂的 SQL 查询。
- Data distribution can become lopsided in a shard. For example, a set of power users on a shard could result in increased load to that shard compared to others.  
	数据分布在分片中可能会出现不平衡。例如，某个分片上的一组超级用户可能会导致该分片的负载高于其他分片。
	- Rebalancing adds additional complexity. A sharding function based on [consistent hashing](http://www.paperplanes.de/2011/12/9/the-magic-of-consistent-hashing.html) can reduce the amount of transferred data.  
		重新平衡会增加复杂性。基于 [一致性哈希的](http://www.paperplanes.de/2011/12/9/the-magic-of-consistent-hashing.html) 分片函数可以减少传输的数据量。
- Joining data from multiple shards is more complex.  
	合并来自多个分片的数据更加复杂。
- Sharding adds more hardware and additional complexity.  
	分片会增加硬件需求和复杂性。

#### Denormalization非规范化

Denormalization attempts to improve read performance at the expense of some write performance. Redundant copies of the data are written in multiple tables to avoid expensive joins. Some RDBMS such as [PostgreSQL](https://en.wikipedia.org/wiki/PostgreSQL) and Oracle support [materialized views](https://en.wikipedia.org/wiki/Materialized_view) which handle the work of storing redundant information and keeping redundant copies consistent.  
反规范化旨在以牺牲部分写入性能为代价来提升读取性能。它将数据的冗余副本写入多个表中，以避免代价高昂的连接操作。一些关系型数据库管理系统（RDBMS），例如 [PostgreSQL](https://en.wikipedia.org/wiki/PostgreSQL) 和 Oracle，支持 [物化视图](https://en.wikipedia.org/wiki/Materialized_view) ，后者负责存储冗余信息并保持冗余副本的一致性。

Once data becomes distributed with techniques such as [federation](#federation) and [sharding](#sharding), managing joins across data centers further increases complexity. Denormalization might circumvent the need for such complex joins.  
一旦数据通过 [联邦](#federation) 和 [分片](#sharding) 等技术实现分布式存储，跨数据中心管理连接操作的复杂性就会进一步增加。反规范化或许可以避免这种复杂的连接操作。

In most systems, reads can heavily outnumber writes 100:1 or even 1000:1. A read resulting in a complex database join can be very expensive, spending a significant amount of time on disk operations.  
在大多数系统中，读取操作的数量可能远远超过写入操作，比例可达 100:1 甚至 1000:1。一次复杂的数据库连接操作可能会非常耗时，因为磁盘操作会消耗大量时间。

##### Disadvantage(s): denormalization缺点：非规范化

- Data is duplicated.  
	数据重复。
- Constraints can help redundant copies of information stay in sync, which increases complexity of the database design.  
	约束可以帮助冗余信息副本保持同步，但这会增加数据库设计的复杂性。
- A denormalized database under heavy write load might perform worse than its normalized counterpart.  
	在高写入负载下，非规范化数据库的性能可能不如规范化数据库。

#### SQL tuningSQL 调优

SQL tuning is a broad topic and many [books](https://www.amazon.com/s/ref=nb_sb_noss_2?url=search-alias%3Daps&field-keywords=sql+tuning) have been written as reference.  
SQL 调优是一个涵盖面很广的主题，已经有很多 [书籍](https://www.amazon.com/s/ref=nb_sb_noss_2?url=search-alias%3Daps&field-keywords=sql+tuning) 作为参考资料出版。

It's important to **benchmark** and **profile** to simulate and uncover bottlenecks.  
通过 **基准测试** 和 **分析** 来模拟和发现瓶颈非常重要。

- **Benchmark** - Simulate high-load situations with tools such as [ab](http://httpd.apache.org/docs/2.2/programs/ab.html).  
	**基准测试** - 使用 [ab](http://httpd.apache.org/docs/2.2/programs/ab.html) 等工具模拟高负载情况。
- **Profile** - Enable tools such as the [slow query log](http://dev.mysql.com/doc/refman/5.7/en/slow-query-log.html) to help track performance issues.  
	**配置文件** - 启用 [慢查询日志](http://dev.mysql.com/doc/refman/5.7/en/slow-query-log.html) 等工具，以帮助跟踪性能问题。

Benchmarking and profiling might point you to the following optimizations.  
基准测试和性能分析可能会为您指出以下优化方向。

##### Tighten up the schema完善方案

- MySQL dumps to disk in contiguous blocks for fast access.  
	为了实现快速访问，MySQL 会将数据以连续块的形式转储到磁盘。
- Use `CHAR` instead of `VARCHAR` for fixed-length fields.  
	对于固定长度字段，请使用 `CHAR` 而不是 `VARCHAR` 。
	- `CHAR` effectively allows for fast, random access, whereas with `VARCHAR`, you must find the end of a string before moving onto the next one.  
		`CHAR` 可以有效地实现快速、随机访问，而 `VARCHAR` 类型则必须先找到字符串的结尾才能访问下一个字符串。
- Use `TEXT` for large blocks of text such as blog posts. `TEXT` also allows for boolean searches. Using a `TEXT` field results in storing a pointer on disk that is used to locate the text block.  
	对于博客文章等大段文本，请使用 `TEXT` 。TEXT `TEXT` 还支持布尔搜索。使用 `TEXT` 字段会在磁盘上存储一个指针，用于定位文本块。
- Use `INT` for larger numbers up to 2^32 or 4 billion.  
	对于大于等于 2^32 或 40 亿的较大数字，请使用 `INT` 。
- Use `DECIMAL` for currency to avoid floating point representation errors.  
	货币数值请使用 `DECIMAL` 以避免浮点表示误差。
- Avoid storing large `BLOBS`, store the location of where to get the object instead.  
	避免存储大型 `BLOBS` ，而应存储获取该对象的位置信息。
- `VARCHAR(255)` is the largest number of characters that can be counted in an 8 bit number, often maximizing the use of a byte in some RDBMS.  
	`VARCHAR(255)` 是一个 8 位数字可以表示的最大字符数，这在某些关系数据库管理系统中通常可以最大限度地利用一个字节。
- Set the `NOT NULL` constraint where applicable to [improve search performance](http://stackoverflow.com/questions/1017239/how-do-null-values-affect-performance-in-a-database-search).  
	在适用的情况下设置 `NOT NULL` 约束以 [提高搜索性能](http://stackoverflow.com/questions/1017239/how-do-null-values-affect-performance-in-a-database-search) 。

##### Use good indices使用好的指数

- Columns that you are querying (`SELECT`, `GROUP BY`, `ORDER BY`, `JOIN`) could be faster with indices.  
	使用索引可以提高查询列（ `SELECT` 、 `GROUP BY` 、 `ORDER BY` 、 `JOIN` ）的速度。
- Indices are usually represented as self-balancing [B-tree](https://en.wikipedia.org/wiki/B-tree) that keeps data sorted and allows searches, sequential access, insertions, and deletions in logarithmic time.  
	索引通常表示为自平衡 [B 树](https://en.wikipedia.org/wiki/B-tree) ，它可以保持数据有序，并允许在对数时间内进行搜索、顺序访问、插入和删除。
- Placing an index can keep the data in memory, requiring more space.  
	设置索引可能会将数据保留在内存中，从而需要更多空间。
- Writes could also be slower since the index also needs to be updated.  
	由于索引也需要更新，写入速度可能会变慢。
- When loading large amounts of data, it might be faster to disable indices, load the data, then rebuild the indices.  
	加载大量数据时，禁用索引、加载数据，然后再重建索引可能会更快。

##### Avoid expensive joins避免昂贵的加入。

- [Denormalize](#denormalization) where performance demands it.  
	在性能需要时 [进行非规范化处理](#denormalization) 。

##### Partition tables分区表

- Break up a table by putting hot spots in a separate table to help keep it in memory.  
	将热点数据放在单独的表中，从而将表拆分，以便更好地保存在内存中。

### NoSQL

NoSQL is a collection of data items represented in a **key-value store**, **document store**, **wide column store**, or a **graph database**. Data is denormalized, and joins are generally done in the application code. Most NoSQL stores lack true ACID transactions and favor [eventual consistency](#eventual-consistency).  
NoSQL 是一种数据集合，数据项以 **键值存储** 、 **文档存储** 、 **宽列存储** 或 **图数据库的** 形式呈现。数据是非规范化的，连接操作通常在应用程序代码中完成。大多数 NoSQL 存储缺乏真正的 ACID 事务，并且倾向于 [最终一致性](#eventual-consistency) 。

**BASE** is often used to describe the properties of NoSQL databases. In comparison with the [CAP Theorem](#cap-theorem), BASE chooses availability over consistency.  
**BASE** 通常用于描述 NoSQL 数据库的特性。与 [CAP 定理](#cap-theorem) 相比，BASE 更注重可用性而非一致性。

- **Basically available** - the system guarantees availability.  
	**基本可用** ——系统保证可用性。
- **Soft state** - the state of the system may change over time, even without input.  
	**软状态** ——即使没有输入，系统状态也可能随时间发生变化。
- **Eventual consistency** - the system will become consistent over a period of time, given that the system doesn't receive input during that period.  
	**最终一致性** ——如果系统在一段时间内没有收到输入，那么系统将在一段时间内趋于一致。

In addition to choosing between [SQL or NoSQL](#sql-or-nosql), it is helpful to understand which type of NoSQL database best fits your use case(s). We'll review **key-value stores**, **document stores**, **wide column stores**, and **graph databases** in the next section.  
除了选择 [SQL 还是 NoSQL](#sql-or-nosql) 之外，了解哪种 NoSQL 数据库最适合您的使用场景也至关重要。下一节我们将介绍 **键值存储** 、 **文档存储** 、 **宽列存储** 和 **图数据库** 。

#### Key-value store键值存储

> Abstraction: hash table  
> 抽象：哈希表

A key-value store generally allows for O(1) reads and writes and is often backed by memory or SSD. Data stores can maintain keys in [lexicographic order](https://en.wikipedia.org/wiki/Lexicographical_order), allowing efficient retrieval of key ranges. Key-value stores can allow for storing of metadata with a value.  
键值存储通常允许 O(1) 的读写操作，并且通常由内存或固态硬盘 (SSD) 提供支持。数据存储可以按 [字典顺序](https://en.wikipedia.org/wiki/Lexicographical_order) 维护键，从而实现对键范围的高效检索。键值存储还可以存储带有值的元数据。

---

Key-value stores provide high performance and are often used for simple data models or for rapidly-changing data, such as an in-memory cache layer.  
键值存储具有高性能，通常用于简单的数据模型或快速变化的数据，例如内存缓存层。  
Since they offer only a limited set of operations, complexity is shifted to the application layer if additional operations are needed.  
由于它们仅提供有限的操作集，因此如果需要额外的操作，复杂性就会转移到应用层。

---

A key-value store is the basis for more complex systems such as a document store, and in some cases, a graph database.  
键值存储是更复杂系统（例如文档存储）的基础，在某些情况下，也是图数据库的基础。

#### Document store文档存储

> Abstraction: key-value store with documents stored as values

A document store is centered around documents (XML, JSON, binary, etc), where a document stores all information for a given object. Document stores provide APIs or a query language to query based on the internal structure of the document itself. *Note, many key-value stores include features for working with a value's metadata, blurring the lines between these two storage types.*  
文档存储以文档（XML、JSON、二进制等）为核心，每个文档存储给定对象的所有信息。文档存储提供 API 或查询语言，以便基于文档自身的内部结构进行查询。 *需要注意的是，许多键值存储也包含处理值元数据的功能，这模糊了这两种存储类型之间的界限。*

Based on the underlying implementation, documents are organized by collections, tags, metadata, or directories. Although documents can be organized or grouped together, documents may have fields that are completely different from each other.  
根据底层实现方式的不同，文档可以按集合、标签、元数据或目录进行组织。虽然文档可以组织或分组，但文档之间可能包含完全不同的字段。

Some document stores like [MongoDB](https://www.mongodb.com/mongodb-architecture) and [CouchDB](https://blog.couchdb.org/2016/08/01/couchdb-2-0-architecture/) also provide a SQL-like language to perform complex queries. [DynamoDB](http://www.read.seas.harvard.edu/~kohler/class/cs239-w08/decandia07dynamo.pdf) supports both key-values and documents.  
一些文档型数据库，例如 [MongoDB](https://www.mongodb.com/mongodb-architecture) 和 [CouchDB](https://blog.couchdb.org/2016/08/01/couchdb-2-0-architecture/) ，也提供类似 SQL 的语言来执行复杂的查询。DynamoDB 同时支持键值对和文档 [类型](http://www.read.seas.harvard.edu/~kohler/class/cs239-w08/decandia07dynamo.pdf) 。

Document stores provide high flexibility and are often used for working with occasionally changing data.  
文档存储具有很高的灵活性，通常用于处理偶尔会发生变化的数据。

宽列式存储具有高可用性和高可扩展性，通常用于处理非常大的数据集。

## Cache缓存

[![](https://github.com/donnemartin/system-design-primer/raw/master/images/Q6z24La.png)](https://github.com/donnemartin/system-design-primer/blob/master/images/Q6z24La.png)  
*[Source: Scalable system design patterns  
来源：可扩展系统设计模式](http://horicky.blogspot.com/2010/10/scalable-system-design-patterns.html)*

Caching improves page load times and can reduce the load on your servers and databases. In this model, the dispatcher will first lookup if the request has been made before and try to find the previous result to return, in order to save the actual execution.  
缓存可以缩短页面加载时间，并减轻服务器和数据库的负载。在这种模式下，调度器会首先查找该请求是否已被发出，并尝试返回之前的结果，以节省实际执行时间。

Databases often benefit from a uniform distribution of reads and writes across its partitions. Popular items can skew the distribution, causing bottlenecks. Putting a cache in front of a database can help absorb uneven loads and spikes in traffic.  
数据库通常受益于读写操作在各个分区间的均匀分布。热门条目会破坏这种分布，导致瓶颈。在数据库前端部署缓存可以帮助缓解负载不均和流量高峰。

### Client caching客户端缓存

Caches can be located on the client side (OS or browser), [server side](#reverse-proxy-web-server), or in a distinct cache layer.  
缓存可以位于客户端（操作系统或浏览器）、 [服务器端](#reverse-proxy-web-server) 或独立的缓存层中。

### CDN cachingCDN 缓存

[CDNs](#content-delivery-network) are considered a type of cache.  
[CDN](#content-delivery-network) 被认为是一种缓存。

### Web server cachingWeb 服务器缓存

[Reverse proxies](#reverse-proxy-web-server) and caches such as [Varnish](https://www.varnish-cache.org/) can serve static and dynamic content directly. Web servers can also cache requests, returning responses without having to contact application servers.  
[反向代理](#reverse-proxy-web-server) 和缓存（例如 [Varnish）](https://www.varnish-cache.org/) 可以直接提供静态和动态内容。Web 服务器还可以缓存请求，无需联系应用服务器即可返回响应。

### Database caching数据库缓存

Your database usually includes some level of caching in a default configuration, optimized for a generic use case. Tweaking these settings for specific usage patterns can further boost performance.  
您的数据库通常在默认配置中包含一定程度的缓存，并针对通用用例进行了优化。针对特定使用模式调整这些设置可以进一步提升性能。

### Application caching应用程序缓存

In-memory caches such as Memcached and Redis are key-value stores between your application and your data storage. Since the data is held in RAM, it is much faster than typical databases where data is stored on disk. RAM is more limited than disk, so [cache invalidation](https://en.wikipedia.org/wiki/Cache_algorithms) algorithms such as [least recently used (LRU)](https://en.wikipedia.org/wiki/Cache_replacement_policies#Least_recently_used_\(LRU\)) can help invalidate 'cold' entries and keep 'hot' data in RAM.  
内存缓存（例如 Memcached 和 Redis）是应用程序和数据存储之间的键值存储。由于数据存储在 RAM 中，因此速度比将数据存储在磁盘上的传统数据库快得多。RAM 的容量比磁盘有限，因此可以 [使用最近最少使用 (LRU)](https://en.wikipedia.org/wiki/Cache_replacement_policies#Least_recently_used_\(LRU\)) 等 [缓存失效](https://en.wikipedia.org/wiki/Cache_algorithms) 算法来使“冷”条目失效，并将“热”数据保留在 RAM 中。

Redis has the following additional features:  
Redis 还具有以下附加功能：

- Persistence option  
	持久化选项
- Built-in data structures such as sorted sets and lists  
	内置数据结构，例如有序集合和列表

There are multiple levels you can cache that fall into two general categories: **database queries** and **objects**:  
您可以缓存多个级别，这些级别大致可分为两类： **数据库查询** 和 **对象** ：

- Row level  
	行级别
- Query-level  
	查询级别
- Fully-formed serializable objects  
	完全成型的可序列化对象
- Fully-rendered HTML  
	完全渲染的 HTML

Generally, you should try to avoid file-based caching, as it makes cloning and auto-scaling more difficult.  
一般来说，你应该尽量避免使用基于文件的缓存，因为它会使克隆和自动扩展变得更加困难。

### Caching at the database query level数据库查询级别的缓存

Whenever you query the database, hash the query as a key and store the result to the cache. This approach suffers from expiration issues:  
每次查询数据库时，将查询语句哈希处理成键，并将结果存储到缓存中。这种方法存在缓存过期的问题：

- Hard to delete a cached result with complex queries  
	使用复杂查询时，很难删除缓存结果。
- If one piece of data changes such as a table cell, you need to delete all cached queries that might include the changed cell  
	如果某个数据项（例如表格单元格）发生更改，则需要删除所有可能包含该已更改单元格的缓存查询。

### Caching at the object level对象级缓存

See your data as an object, similar to what you do with your application code. Have your application assemble the dataset from the database into a class instance or a data structure(s):  
将数据视为对象，就像处理应用程序代码一样。让应用程序将数据库中的数据集组装成类实例或数据结构：

- Remove the object from cache if its underlying data has changed  
	如果对象的底层数据已更改，则从缓存中移除该对象。
- Allows for asynchronous processing: workers assemble objects by consuming the latest cached object  
	允许异步处理：工作进程通过消费最新的缓存对象来组装对象。

Suggestions of what to cache:  
缓存建议：

- User sessions  
	用户会话
- Fully rendered web pages  
	完全渲染的网页
- Activity streams  
	活动流
- User graph data  
	用户图数据

### When to update the cache何时更新缓存

Since you can only store a limited amount of data in cache, you'll need to determine which cache update strategy works best for your use case.  
由于缓存中只能存储有限量的数据，因此您需要确定哪种缓存更新策略最适合您的使用场景。

#### Cache-aside缓存旁

*[Source: From cache to in-memory data grid  
来源：从缓存到内存数据网格](http://www.slideshare.net/tmatyashovsky/from-cache-to-in-memory-data-grid-introduction-to-hazelcast)*

The application is responsible for reading and writing from storage. The cache does not interact with storage directly. The application does the following:  
应用程序负责从存储器读取和写入数据。缓存不直接与存储器交互。应用程序执行以下操作：

- Look for entry in cache, resulting in a cache miss  
	查找缓存条目，导致缓存未命中
- Load entry from the database  
	从数据库加载条目
- Add entry to cache  
	向缓存添加条目
- Return entry  
	返回条目
```
def get_user(self, user_id):
    user = cache.get("user.{0}", user_id)
    if user is None:
        user = db.query("SELECT * FROM users WHERE user_id = {0}", user_id)
        if user is not None:
            key = "user.{0}".format(user_id)
            cache.set(key, json.dumps(user))
    return user
```

[Memcached](https://memcached.org/) is generally used in this manner.  
[Memcached](https://memcached.org/) 通常就是这样使用的。

Subsequent reads of data added to cache are fast. Cache-aside is also referred to as lazy loading. Only requested data is cached, which avoids filling up the cache with data that isn't requested.  
后续读取缓存中的数据速度很快。缓存旁路技术也称为延迟加载。只有请求的数据才会被缓存，这样可以避免缓存中填充未被请求的数据。

##### Disadvantage(s): cache-aside缺点：缓存旁

- Each cache miss results in three trips, which can cause a noticeable delay.  
	每次缓存未命中都会导致三次往返，这可能会造成明显的延误。
- Data can become stale if it is updated in the database. This issue is mitigated by setting a time-to-live (TTL) which forces an update of the cache entry, or by using write-through.  
	如果数据库中的数据被更新，则数据可能会过期。可以通过设置生存时间 (TTL) 来缓解此问题，TTL 会强制更新缓存条目，或者使用直写方式。
- When a node fails, it is replaced by a new, empty node, increasing latency.  
	当一个节点发生故障时，它会被一个新的空节点替换，从而增加延迟。

#### Write-through通写式

[![](https://github.com/donnemartin/system-design-primer/raw/master/images/0vBc0hN.png)](https://github.com/donnemartin/system-design-primer/blob/master/images/0vBc0hN.png)  
*[Source: Scalability, availability, stability, patterns  
来源：可扩展性、可用性、稳定性、模式](http://www.slideshare.net/jboner/scalability-availability-stability-patterns/)*

The application uses the cache as the main data store, reading and writing data to it, while the cache is responsible for reading and writing to the database:  
该应用程序使用缓存作为主要数据存储，对缓存进行数据读写操作，而缓存则负责对数据库进行数据读写操作：

- Application adds/updates entry in cache  
	应用程序在缓存中添加/更新条目
- Cache synchronously writes entry to data store  
	缓存同步地将条目写入数据存储
- Return  
	返回

Application code:  
应用程序代码：

```
set_user(12345, {"foo":"bar"})
```

Cache code:  
缓存代码：

```
def set_user(user_id, values):
    user = db.query("UPDATE Users WHERE id = {0}", user_id, values)
    cache.set(user_id, user)
```

Write-through is a slow overall operation due to the write operation, but subsequent reads of just written data are fast. Users are generally more tolerant of latency when updating data than reading data. Data in the cache is not stale.  
由于写入操作本身较慢，因此直写式操作整体速度较慢，但后续读取已写入的数据速度很快。用户通常对更新数据的延迟容忍度高于读取数据。缓存中的数据不会过期。

##### Disadvantage(s): write through缺点：通读

- When a new node is created due to failure or scaling, the new node will not cache entries until the entry is updated in the database. Cache-aside in conjunction with write through can mitigate this issue.  
	当因故障或扩容而创建新节点时，新节点不会缓存条目，直到数据库中的条目被更新。缓存旁路（Cache-side）结合直写（Write-Through）可以缓解此问题。
- Most data written might never be read, which can be minimized with a TTL.  
	写入的大部分数据可能永远不会被读取，而使用 TTL 可以最大限度地减少这种情况。

#### Write-behind (write-back)后写（回写）

[![](https://github.com/donnemartin/system-design-primer/raw/master/images/rgSrvjG.png)](https://github.com/donnemartin/system-design-primer/blob/master/images/rgSrvjG.png)  
*[Source: Scalability, availability, stability, patterns  
来源：可扩展性、可用性、稳定性、模式](http://www.slideshare.net/jboner/scalability-availability-stability-patterns/)*

In write-behind, the application does the following:  
在写入后置模式下，应用程序执行以下操作：

- Add/update entry in cache  
	在缓存中添加/更新条目
- Asynchronously write entry to the data store, improving write performance  
	异步写入数据存储条目，提高写入性能

##### Disadvantage(s): write-behind缺点：后写式

- There could be data loss if the cache goes down prior to its contents hitting the data store.  
	如果缓存在其内容到达数据存储之前发生故障，则可能会丢失数据。
- It is more complex to implement write-behind than it is to implement cache-aside or write-through.  
	实现后写式比实现缓存旁写式或直写式更复杂。

#### Refresh-ahead提前刷新

[![](https://github.com/donnemartin/system-design-primer/raw/master/images/kxtjqgE.png)](https://github.com/donnemartin/system-design-primer/blob/master/images/kxtjqgE.png)  
*[Source: From cache to in-memory data grid  
来源：从缓存到内存数据网格](http://www.slideshare.net/tmatyashovsky/from-cache-to-in-memory-data-grid-introduction-to-hazelcast)*

You can configure the cache to automatically refresh any recently accessed cache entry prior to its expiration.  
您可以配置缓存，使其在最近访问过的缓存条目过期之前自动刷新。

Refresh-ahead can result in reduced latency vs read-through if the cache can accurately predict which items are likely to be needed in the future.  
如果缓存能够准确预测将来可能需要哪些项目，那么与直接读取相比，提前刷新可以降低延迟。

##### Disadvantage(s): refresh-ahead缺点：提前刷新

- Not accurately predicting which items are likely to be needed in the future can result in reduced performance than without refresh-ahead.  
	不能准确预测未来可能需要哪些项目，可能会导致性能低于不进行提前刷新的情况。

### Disadvantage(s): cache缺点：缓存

- Need to maintain consistency between caches and the source of truth such as the database through [cache invalidation](https://en.wikipedia.org/wiki/Cache_algorithms).  
	需要通过 [缓存失效](https://en.wikipedia.org/wiki/Cache_algorithms) 来保持缓存与数据库等数据源之间的一致性。
- Cache invalidation is a difficult problem, there is additional complexity associated with when to update the cache.  
	缓存失效是一个难题，何时更新缓存也带来了额外的复杂性。
- Need to make application changes such as adding Redis or memcached.  
	需要对应用程序进行一些更改，例如添加 Redis 或 memcached。

## Asynchronism异步性

[![](https://github.com/donnemartin/system-design-primer/raw/master/images/54GYsSx.png)](https://github.com/donnemartin/system-design-primer/blob/master/images/54GYsSx.png)  
*[Source: Intro to architecting systems for scale  
来源：《可扩展系统架构入门》](http://lethain.com/introduction-to-architecting-systems-for-scale/#platform_layer)*

Asynchronous workflows help reduce request times for expensive operations that would otherwise be performed in-line. They can also help by doing time-consuming work in advance, such as periodic aggregation of data.  
异步工作流有助于减少原本需要在线执行的耗时操作的请求时间。它们还可以预先执行耗时的工作，例如定期数据聚合。

### Message queues消息队列

Message queues receive, hold, and deliver messages. If an operation is too slow to perform inline, you can use a message queue with the following workflow:  
消息队列用于接收、保存和传递消息。如果某个操作速度太慢而无法直接执行，则可以使用消息队列，工作流程如下：

- An application publishes a job to the queue, then notifies the user of job status  
	应用程序将作业发布到队列中，然后通知用户作业状态
- A worker picks up the job from the queue, processes it, then signals the job is complete  
	工作进程从队列中领取任务，处理完毕后发出任务完成的信号。

---

The user is not blocked and the job is processed in the background. During this time, the client might optionally do a small amount of processing to make it seem like the task has completed.  
用户不会被阻塞，任务会在后台处理。在此期间，客户端可能会选择性地执行少量处理操作，使任务看起来像是已经完成。  
For example, if posting a tweet, the tweet could be instantly posted to your timeline, but it could take some time before your tweet is actually delivered to all of your followers.  
例如，如果您发布一条推文，该推文可能会立即发布到您的时间线上，但可能需要一些时间才能真正送达您的所有关注者。

---

**[Redis](https://redis.io/)** is useful as a simple message broker but messages can be lost.  
**[Redis](https://redis.io/)** 作为简单的消息代理很有用，但消息可能会丢失。

**[RabbitMQ](https://www.rabbitmq.com/)** is popular but requires you to adapt to the 'AMQP' protocol and manage your own nodes.  
**[RabbitMQ](https://www.rabbitmq.com/)** 很流行，但需要您适应“AMQP”协议并管理自己的节点。

**[Amazon SQS](https://aws.amazon.com/sqs/)** is hosted but can have high latency and has the possibility of messages being delivered twice.  
**[Amazon SQS](https://aws.amazon.com/sqs/)** 是托管服务，但可能存在高延迟，并且有可能出现消息被重复发送的情况。

### Task queues任务队列

Tasks queues receive tasks and their related data, runs them, then delivers their results. They can support scheduling and can be used to run computationally-intensive jobs in the background.  
任务队列接收任务及其相关数据，运行任务，然后返回结果。它们可以支持任务调度，并可用于在后台运行计算密集型作业。

**[Celery](https://docs.celeryproject.org/en/stable/)** has support for scheduling and primarily has python support.  
**[Celery](https://docs.celeryproject.org/en/stable/)** 支持日程安排，并且主要支持 Python。

### Back pressure反压

---

If queues start to grow significantly, the queue size can become larger than memory, resulting in cache misses, disk reads, and even slower performance. [Back pressure](http://mechanical-sympathy.blogspot.com/2012/05/apply-back-pressure-when-overloaded.html) can help by limiting the queue size, thereby maintaining a high throughput rate and good response times for jobs already in the queue. Once the queue fills up, clients get a server busy or HTTP 503 status code to try again later.  
如果队列开始显著增长，队列大小可能会超过内存容量，导致缓存未命中、磁盘读取，甚至性能下降。 [反压机制](http://mechanical-sympathy.blogspot.com/2012/05/apply-back-pressure-when-overloaded.html) 可以通过限制队列大小来缓解这个问题，从而保持较高的吞吐量和队列中已加载作业的良好响应时间。一旦队列填满，客户端将收到服务器繁忙或 HTTP 503 状态码，提示稍后重试。  
Clients can retry the request at a later time, perhaps with [exponential backoff](https://en.wikipedia.org/wiki/Exponential_backoff).  
客户端可以在稍后的时间重试请求，或许可以采用 [指数退避策略](https://en.wikipedia.org/wiki/Exponential_backoff) 。

---

### Disadvantage(s): asynchronism缺点：异步性

- Use cases such as inexpensive calculations and realtime workflows might be better suited for synchronous operations, as introducing queues can add delays and complexity.  
	对于低成本计算和实时工作流程等用例，同步操作可能更合适，因为引入队列会增加延迟和复杂性。

### Hypertext transfer protocol (HTTP)超文本传输协议（HTTP）

---

HTTP is a method for encoding and transporting data between a client and a server. It is a request/response protocol: clients issue requests and servers issue responses with relevant content and completion status info about the request.  
HTTP 是一种用于在客户端和服务器之间编码和传输数据的方法。它是一种请求/响应协议：客户端发出请求，服务器发出包含相关内容和请求完成状态信息的响应。  
HTTP is self-contained, allowing requests and responses to flow through many intermediate routers and servers that perform load balancing, caching, encryption, and compression.  
HTTP 是自包含的，允许请求和响应流经许多中间路由器和服务器，这些路由器和服务器执行负载均衡、缓存、加密和压缩。

---

A basic HTTP request consists of a verb (method) and a resource (endpoint). Below are common HTTP verbs:  
一个基本的 HTTP 请求由一个动词（方法）和一个资源（端点）组成。以下是一些常见的 HTTP 动词：

| Verb   动词 | Description   描述 | Idempotent\*   幂等\* | Safe   安全的 | Cacheable   可缓存 |
| --- | --- | --- | --- | --- |
| GET | Reads a resource   阅读资源 | Yes   是的 | Yes   是的 | Yes   是的 |
| POST | Creates a resource or trigger a process that handles data   创建资源或触发处理数据的流程 | No   不 | No   不 | Yes if response contains freshness info   如果回复包含新鲜度信息，则为“是”。 |
| PUT | Creates or replace a resource   创建或替换资源 | Yes   是的 | No   不 | No   不 |
| PATCH | Partially updates a resource   部分更新资源 | No   不 | No   不 | Yes if response contains freshness info   如果回复包含新鲜度信息，则为“是”。 |
| DELETE | Deletes a resource   删除资源 | Yes   是的 | No   不 | No   不 |

\*Can be called many times without different outcomes.  
\*可以多次拨打，结果不变。

HTTP is an application layer protocol relying on lower-level protocols such as **TCP** and **UDP**.  
HTTP 是一种应用层协议，它依赖于 **TCP** 和 **UDP** 等底层协议。

### Transmission control protocol (TCP)传输控制协议（TCP）

[![](https://github.com/donnemartin/system-design-primer/raw/master/images/JdAsdvG.jpg)](https://github.com/donnemartin/system-design-primer/blob/master/images/JdAsdvG.jpg)  
*[Source: How to make a multiplayer game  
来源：如何制作多人游戏](http://www.wildbunny.co.uk/blog/2012/10/09/how-to-make-a-multi-player-game-part-1/)*

TCP is a connection-oriented protocol over an [IP network](https://en.wikipedia.org/wiki/Internet_Protocol). Connection is established and terminated using a [handshake](https://en.wikipedia.org/wiki/Handshaking). All packets sent are guaranteed to reach the destination in the original order and without corruption through:  
TCP 是一种基于 [IP 网络的](https://en.wikipedia.org/wiki/Internet_Protocol) 面向连接的协议。连接通过 [握手](https://en.wikipedia.org/wiki/Handshaking) 建立和终止。所有发送的数据包都能保证按原始顺序无损地到达目的地，其机制如下：

- Sequence numbers and [checksum fields](https://en.wikipedia.org/wiki/Transmission_Control_Protocol#Checksum_computation) for each packet  
	每个数据包的序列号和 [校验和字段](https://en.wikipedia.org/wiki/Transmission_Control_Protocol#Checksum_computation)
- [Acknowledgement](https://en.wikipedia.org/wiki/Acknowledgement_\(data_networks\)) packets and automatic retransmission  
	[确认](https://en.wikipedia.org/wiki/Acknowledgement_\(data_networks\)) 包和自动重传

If the sender does not receive a correct response, it will resend the packets. If there are multiple timeouts, the connection is dropped. TCP also implements [flow control](https://en.wikipedia.org/wiki/Flow_control_\(data\)) and [congestion control](https://en.wikipedia.org/wiki/Network_congestion#Congestion_control). These guarantees cause delays and generally result in less efficient transmission than UDP.  
如果发送方没有收到正确的响应，它会重新发送数据包。如果出现多次超时，连接将被断开。TCP 还实现了 [流量控制](https://en.wikipedia.org/wiki/Flow_control_\(data\)) 和 [拥塞控制](https://en.wikipedia.org/wiki/Network_congestion#Congestion_control) 。这些机制会导致延迟，并且通常比 UDP 的传输效率低。

To ensure high throughput, web servers can keep a large number of TCP connections open, resulting in high memory usage. It can be expensive to have a large number of open connections between web server threads and say, a [memcached](https://memcached.org/) server. [Connection pooling](https://en.wikipedia.org/wiki/Connection_pool) can help in addition to switching to UDP where applicable.  
为了确保高吞吐量，Web 服务器可以保持大量 TCP 连接打开，这会导致内存占用过高。在 Web 服务器线程和 [memcached](https://memcached.org/) 服务器等对象之间保持大量打开的连接会消耗大量资源。除了在适用情况下切换到 UDP 协议外 [，连接池](https://en.wikipedia.org/wiki/Connection_pool) 也能有所帮助。

TCP is useful for applications that require high reliability but are less time critical. Some examples include web servers, database info, SMTP, FTP, and SSH.  
TCP 适用于对可靠性要求高但对时间要求不高的应用。例如，Web 服务器、数据库信息、SMTP、FTP 和 SSH 等都使用 TCP 协议。

Use TCP over UDP when:  
在以下情况下使用 TCP 而非 UDP：

- You need all of the data to arrive intact  
	你需要所有数据完好无损地到达。
- You want to automatically make a best estimate use of the network throughput  
	您希望自动对网络吞吐量进行最佳估算利用。

### User datagram protocol (UDP)用户数据报协议（UDP）

[![](https://github.com/donnemartin/system-design-primer/raw/master/images/yzDrJtA.jpg)](https://github.com/donnemartin/system-design-primer/blob/master/images/yzDrJtA.jpg)  
*[Source: How to make a multiplayer game  
来源：如何制作多人游戏](http://www.wildbunny.co.uk/blog/2012/10/09/how-to-make-a-multi-player-game-part-1/)*

---

UDP is connectionless. Datagrams (analogous to packets) are guaranteed only at the datagram level. Datagrams might reach their destination out of order or not at all. UDP does not support congestion control.  
UDP 是无连接的。数据报（类似于数据包）的质量保证仅限于数据报层面。数据报可能乱序到达目的地，甚至根本无法到达。UDP 不支持拥塞控制。  
Without the guarantees that TCP support, UDP is generally more efficient.  
如果没有 TCP 支持的保证，UDP 通常效率更高。

---

UDP can broadcast, sending datagrams to all devices on the subnet. This is useful with [DHCP](https://en.wikipedia.org/wiki/Dynamic_Host_Configuration_Protocol) because the client has not yet received an IP address, thus preventing a way for TCP to stream without the IP address.  
UDP 可以广播数据报，将数据报发送到子网上的所有设备。这在 [DHCP](https://en.wikipedia.org/wiki/Dynamic_Host_Configuration_Protocol) 环境下非常有用，因为客户端尚未收到 IP 地址，从而阻止了 TCP 在没有 IP 地址的情况下进行数据流传输。

UDP is less reliable but works well in real time use cases such as VoIP, video chat, streaming, and realtime multiplayer games.  
UDP 的可靠性较低，但在 VoIP、视频聊天、流媒体和实时多人游戏等实时应用场景中表现良好。

Use UDP over TCP when:  
在以下情况下使用 UDP 而非 TCP：

- You need the lowest latency  
	你需要最低的延迟。
- Late data is worse than loss of data  
	数据延迟比数据丢失更糟糕。
- You want to implement your own error correction  
	你想实现自己的纠错机制。

### Remote procedure call (RPC)远程过程调用（RPC）

[![](https://github.com/donnemartin/system-design-primer/raw/master/images/iF4Mkb5.png)](https://github.com/donnemartin/system-design-primer/blob/master/images/iF4Mkb5.png)  
*[Source: Crack the system design interview  
来源：破解系统设计面试](http://www.puncsky.com/blog/2016-02-13-crack-the-system-design-interview)*

---

In an RPC, a client causes a procedure to execute on a different address space, usually a remote server. The procedure is coded as if it were a local procedure call, abstracting away the details of how to communicate with the server from the client program.  
在远程过程调用（RPC）中，客户端会触发一个过程在不同的地址空间（通常是远程服务器）上执行。该过程的编码方式与本地过程调用相同，从而将如何与服务器通信的细节对客户端程序进行了抽象。  
Remote calls are usually slower and less reliable than local calls so it is helpful to distinguish RPC calls from local calls.  
远程调用通常比本地调用速度慢、可靠性低，因此区分 RPC 调用和本地调用很有帮助。  
Popular RPC frameworks include [Protobuf](https://developers.google.com/protocol-buffers/), [Thrift](https://thrift.apache.org/), and [Avro](https://avro.apache.org/docs/current/).  
流行的 RPC 框架包括 [Protobuf](https://developers.google.com/protocol-buffers/) 、 [Thrift](https://thrift.apache.org/) 和 [Avro](https://avro.apache.org/docs/current/) 。

---

RPC is a request-response protocol:  
RPC 是一种请求-响应协议：

- **Client program** - Calls the client stub procedure. The parameters are pushed onto the stack like a local procedure call.  
	**客户端程序** ——调用客户端存根过程。参数像本地过程调用一样被压入堆栈。
- **Client stub procedure** - Marshals (packs) procedure id and arguments into a request message.  
	**客户端存根过程** - 将过程 ID 和参数打包到请求消息中。
- **Client communication module** - OS sends the message from the client to the server.  
	**客户端通信模块** - 操作系统将消息从客户端发送到服务器。
- **Server communication module** - OS passes the incoming packets to the server stub procedure.  
	**服务器通信模块** - 操作系统将传入的数据包传递给服务器存根过程。
- **Server stub procedure** - Unmarshalls the results, calls the server procedure matching the procedure id and passes the given arguments.  
	**服务器存根过程** - 反序列化结果，调用与过程 ID 匹配的服务器过程，并传递给定的参数。
- The server response repeats the steps above in reverse order.  
	服务器响应会按相反的顺序重复上述步骤。

Sample RPC calls:  
RPC 调用示例：

```
GET /someoperation?data=anId

POST /anotheroperation
{
  "data":"anId";
  "anotherdata": "another value"
}
```

RPC is focused on exposing behaviors. RPCs are often used for performance reasons with internal communications, as you can hand-craft native calls to better fit your use cases.  
RPC 的重点在于暴露行为。出于性能考虑，RPC 通常用于内部通信，因为您可以手动编写原生调用以更好地满足您的使用场景。

Choose a native library (aka SDK) when:  
在以下情况下选择原生库（也称为 SDK）：

- You know your target platform.  
	您了解您的目标平台。
- You want to control how your "logic" is accessed.  
	你想控制别人如何访问你的“逻辑”。
- You want to control how error control happens off your library.  
	你想控制库之外的错误处理方式。
- Performance and end user experience is your primary concern.  
	性能和最终用户体验是您的首要考虑因素。

HTTP APIs following **REST** tend to be used more often for public APIs.  
遵循 **REST 规范的** HTTP API 通常更常用于公共 API。

#### Disadvantage(s): RPC缺点：RPC

- RPC clients become tightly coupled to the service implementation.  
	RPC 客户端与服务实现紧密耦合。
- A new API must be defined for every new operation or use case.  
	每新增一项操作或用例，都需要定义一个新的 API。
- It can be difficult to debug RPC.  
	调试 RPC 可能很困难。
- You might not be able to leverage existing technologies out of the box. For example, it might require additional effort to ensure [RPC calls are properly cached](https://web.archive.org/web/20170608193645/http://etherealbits.com/2012/12/debunking-the-myths-of-rpc-rest/) on caching servers such as [Squid](http://www.squid-cache.org/).  
	你可能无法直接利用现有技术。例如，可能需要额外努力来确保 RPC 调用在 [Squid](http://www.squid-cache.org/) 等缓存服务器上 [得到正确缓存](https://web.archive.org/web/20170608193645/http://etherealbits.com/2012/12/debunking-the-myths-of-rpc-rest/) 。

### Representational state transfer (REST)表述性状态转移（REST）

---

REST is an architectural style enforcing a client/server model where the client acts on a set of resources managed by the server. The server provides a representation of resources and actions that can either manipulate or get a new representation of resources.  
REST 是一种架构风格，它采用客户端/服务器模型，其中客户端操作由服务器管理的一组资源。服务器提供资源的表示形式以及可以操作资源或获取资源新表示形式的操作。  
All communication must be stateless and cacheable.  
所有通信都必须是无状态的且可缓存的。

---

There are four qualities of a RESTful interface:  
RESTful 接口具有四个特点：

- **Identify resources (URI in HTTP)** - use the same URI regardless of any operation.  
	**标识资源（HTTP 中的 URI）** - 无论进行任何操作，都使用相同的 URI。
- **Change with representations (Verbs in HTTP)** - use verbs, headers, and body.  
	**使用表示形式（HTTP 中的动词）进行更改** - 使用动词、标头和正文。
- **Self-descriptive error message (status response in HTTP)** - Use status codes, don't reinvent the wheel.  
	**自描述性错误消息（HTTP 中的状态响应）** - 使用状态代码，不要重复造轮子。
- **[HATEOAS](http://restcookbook.com/Basics/hateoas/) (HTML interface for HTTP)** - your web service should be fully accessible in a browser.  
	**[HATEOAS](http://restcookbook.com/Basics/hateoas/) （HTTP 的 HTML 接口）** ——您的 Web 服务应该可以在浏览器中完全访问。

Sample REST calls:  
REST 调用示例：

```
GET /someresources/anId

PUT /someresources/anId
{"anotherdata": "another value"}
```

REST is focused on exposing data. It minimizes the coupling between client/server and is often used for public HTTP APIs. REST uses a more generic and uniform method of exposing resources through URIs, [representation through headers](https://github.com/for-GET/know-your-http-well/blob/master/headers.md), and actions through verbs such as GET, POST, PUT, DELETE, and PATCH. Being stateless, REST is great for horizontal scaling and partitioning.  
REST 专注于数据暴露。它最大限度地降低了客户端/服务器之间的耦合度，常用于公共 HTTP API。REST 使用更通用、更统一的方法，通过 URI 暴露资源， [通过请求头表示数据](https://github.com/for-GET/know-your-http-well/blob/master/headers.md) ，并通过 GET、POST、PUT、DELETE 和 PATCH 等动词执行操作。由于 REST 是无状态的，因此非常适合横向扩展和分区。

#### Disadvantage(s): REST缺点：休息

---

- With REST being focused on exposing data, it might not be a good fit if resources are not naturally organized or accessed in a simple hierarchy. For example, returning all updated records from the past hour matching a particular set of events is not easily expressed as a path.  
	由于 REST 侧重于暴露数据，因此如果资源没有以简单的层级结构自然组织或访问，它可能就不太适用。例如，返回过去一小时内所有符合特定事件集的更新记录，很难用路径来表示。  
	With REST, it is likely to be implemented with a combination of URI path, query parameters, and possibly the request body.  
	使用 REST 时，很可能是通过 URI 路径、查询参数以及可能的请求正文的组合来实现的。

---

- REST typically relies on a few verbs (GET, POST, PUT, DELETE, and PATCH) which sometimes doesn't fit your use case. For example, moving expired documents to the archive folder might not cleanly fit within these verbs.  
	REST 通常依赖于几个动词（GET、POST、PUT、DELETE 和 PATCH），但有时这些动词并不完全符合您的使用场景。例如，将过期文档移动到归档文件夹可能并不适合使用这些动词。

---

- Fetching complicated resources with nested hierarchies requires multiple round trips between the client and server to render single views, e.g. fetching content of a blog entry and the comments on that entry.  
	获取具有嵌套层次结构的复杂资源需要客户端和服务器之间多次往返才能渲染单个视图，例如获取博客文章的内容和该文章的评论。  
	For mobile applications operating in variable network conditions, these multiple roundtrips are highly undesirable.  
	对于在网络状况不稳定的情况下运行的移动应用程序而言，这种多次往返是非常不理想的。

---

- Over time, more fields might be added to an API response and older clients will receive all new data fields, even those that they do not need, as a result, it bloats the payload size and leads to larger latencies.  
	随着时间的推移，API 响应中可能会添加更多字段，而旧客户端将收到所有新的数据字段，即使是它们不需要的字段，这会导致有效负载大小膨胀，从而导致更大的延迟。

## Security安全

This section could use some updates. Consider [contributing](#contributing)!

Security is a broad topic. Unless you have considerable experience, a security background, or are applying for a position that requires knowledge of security, you probably won't need to know more than the basics:  
安全是一个涵盖面很广的话题。除非你拥有丰富的经验、安全背景，或者你申请的职位需要具备安全知识，否则你可能只需要了解一些基础知识即可：

- Encrypt in transit and at rest.  
	传输中和静态数据均需加密。
- Sanitize all user inputs or any input parameters exposed to user to prevent [XSS](https://en.wikipedia.org/wiki/Cross-site_scripting) and [SQL injection](https://en.wikipedia.org/wiki/SQL_injection).  
	对所有用户输入或任何暴露给用户的输入参数进行清理，以防止 [XSS](https://en.wikipedia.org/wiki/Cross-site_scripting) 和 [SQL 注入](https://en.wikipedia.org/wiki/SQL_injection) 。
- Use parameterized queries to prevent SQL injection.  
	使用参数化查询可以防止 SQL 注入。
- Use the principle of [least privilege](https://en.wikipedia.org/wiki/Principle_of_least_privilege).  
	遵循 [最小权限](https://en.wikipedia.org/wiki/Principle_of_least_privilege) 原则。
