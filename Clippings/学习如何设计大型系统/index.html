Performance vs scalability性能与可扩展性

A service is scalable if it results in increased performance in a manner proportional to resources added. Generally, increasing performance means serving more units of work, but it can also be to handle larger units of work, such as when datasets grow.1
如果一项服务能够以与资源增加成比例的方式提升 性能 ，则称该服务具有 可扩展性 。通常，提升性能意味着处理更多的工作单元，但也可能意味着处理更大的工作单元，例如当数据集增长时。 1

Another way to look at performance vs scalability:

  • If you have a performance problem, your system is slow for a single user.
    如果出现 性能 问题，则表示您的系统对于单个用户来说运行缓慢。
  • If you have a scalability problem, your system is fast for a single user but slow under heavy load.
    如果你的系统存在 可扩展性 问题，那么在单个用户使用时速度很快，但在高负载下速度会变慢。

Availability vs consistency

CAP theorem


Source: CAP theorem revisited

In a distributed computer system, you can only support two of the following guarantees:

  • Consistency - Every read receives the most recent write or an error
  • Availability - Every request receives a response, without guarantee that it contains the most recent version of the information
  • Partition Tolerance - The system continues to operate despite arbitrary partitioning due to network failures

Networks aren't reliable, so you'll need to support partition tolerance. You'll need to make a software tradeoff between consistency and availability.

CP - consistency and partition tolerance

Waiting for a response from the partitioned node might result in a timeout error. CP is a good choice if your business needs require atomic reads and writes.

AP - availability and partition tolerance

Responses return the most readily available version of the data available on any node, which might not be the latest. Writes might take some time to propagate when the partition is resolved.

AP is a good choice if the business needs to allow for eventual consistency or when the system needs to continue working despite external errors.

Consistency patterns一致性模式

With multiple copies of the same data, we are faced with options on how to synchronize them so clients have a consistent view of the data. Recall the definition of consistency from the CAP theorem - Every read receives the most recent write or an error.
当存在同一数据的多个副本时，我们需要选择几种同步方式，以确保客户端能够获得一致的数据视图。回顾一下 CAP 定理 中对一致性的定义——每次读取操作要么接收到最近一次写入的数据，要么接收到错误信息。

Weak consistency一致性较弱

After a write, reads may or may not see it. A best effort approach is taken.
写入操作完成后，读取操作可能看到该数据，也可能看不到。系统会尽力而为。

This approach is seen in systems such as memcached. Weak consistency works well in real time use cases such as VoIP, video chat, and realtime multiplayer games.
这种方法常见于 memcached 等系统中。弱一致性在 VoIP、视频聊天和实时多人游戏等实时应用场景中表现良好。
For example, if you are on a phone call and lose reception for a few seconds, when you regain connection you do not hear what was spoken during connection loss.
例如，如果您正在打电话，但信号中断了几秒钟，当您恢复连接时，您将听不到在信号中断期间说的话。

Eventual consistency最终一致性

After a write, reads will eventually see it (typically within milliseconds). Data is replicated asynchronously.
写入操作完成后，读取操作最终会检测到数据（通常在几毫秒内）。数据以异步方式复制。

This approach is seen in systems such as DNS and email. Eventual consistency works well in highly available systems.
这种方法常见于 DNS 和电子邮件等系统中。最终一致性在高可用性系统中效果显著。

Strong consistency高度一致性

After a write, reads will see it. Data is replicated synchronously.
写入操作完成后，读取操作即可看到更新。数据以同步方式复制。

This approach is seen in file systems and RDBMSes. Strong consistency works well in systems that need transactions.
这种方法常见于文件系统和关系数据库管理系统（RDBMS）。强一致性在需要事务处理的系统中效果显著。

Availability patterns

There are two complementary patterns to support high availability: fail-over and replication.

Fail-over

Active-passive

With active-passive fail-over, heartbeats are sent between the active and the passive server on standby. If the heartbeat is interrupted, the passive server takes over the active's IP address and resumes service.

The length of downtime is determined by whether the passive server is already running in 'hot' standby or whether it needs to start up from 'cold' standby. Only the active server handles traffic.

Active-passive failover can also be referred to as master-slave failover.

Active-active

In active-active, both servers are managing traffic, spreading the load between them.

If the servers are public-facing, the DNS would need to know about the public IPs of both servers. If the servers are internal-facing, application logic would need to know about both servers.

Active-active failover can also be referred to as master-master failover.

Disadvantage(s): failover

  • Fail-over adds more hardware and additional complexity.
  • There is a potential for loss of data if the active system fails before any newly written data can be replicated to the passive.

If both Foo and Bar each had 99.9% availability, their total availability in parallel would be 99.9999%.

Content delivery network内容分发网络


Source: Why use a CDN
来源：为什么要使用 CDN

A content delivery network (CDN) is a globally distributed network of proxy servers, serving content from locations closer to the user.
内容分发网络 (CDN) 是一个全球分布式的代理服务器网络，从距离用户更近的位置提供内容。
Generally, static files such as HTML/CSS/JS, photos, and videos are served from CDN, although some CDNs such as Amazon's CloudFront support dynamic content. The site's DNS resolution will tell clients which server to contact.
通常情况下，静态文件（例如 HTML/CSS/JS、图片和视频）由 CDN 提供，不过也有一些 CDN（例如亚马逊的 CloudFront）支持动态内容。网站的 DNS 解析会告诉客户端应该联系哪个服务器。

Serving content from CDNs can significantly improve performance in two ways:
通过 CDN 提供内容可以从两个方面显著提高性能：

  • Users receive content from data centers close to them
    用户从离他们较近的数据中心接收内容。
  • Your servers do not have to serve requests that the CDN fulfills
    您的服务器无需处理由 CDN 处理的请求。

Push CDNs推送 CDN

Push CDNs receive new content whenever changes occur on your server. You take full responsibility for providing content, uploading directly to the CDN and rewriting URLs to point to the CDN. You can configure when content expires and when it is updated.
推送式 CDN 会在您的服务器上发生更改时接收新内容。您需要全权负责提供内容、直接上传到 CDN 以及重写 URL 以指向 CDN。您可以配置内容的过期时间和更新时间。
Content is uploaded only when it is new or changed, minimizing traffic, but maximizing storage.
内容仅在新增或更改时上传，从而最大限度地减少流量，同时最大限度地利用存储空间。

Sites with a small amount of traffic or sites with content that isn't often updated work well with push CDNs. Content is placed on the CDNs once, instead of being re-pulled at regular intervals.
流量较小或内容更新频率不高的网站非常适合使用推送式 CDN。内容只需在 CDN 上放置一次，无需定期重新拉取。

Pull CDNs拉取 CDN

Pull CDNs grab new content from your server when the first user requests the content. You leave the content on your server and rewrite URLs to point to the CDN. This results in a slower request until the content is cached on the CDN.
拉取式 CDN 会在第一个用户请求内容时从您的服务器获取新内容。您将内容保留在服务器上，并将 URL 重写为指向 CDN。这会导致请求速度变慢，直到内容缓存到 CDN 上为止。

A time-to-live (TTL) determines how long content is cached. Pull CDNs minimize storage space on the CDN, but can create redundant traffic if files expire and are pulled before they have actually changed.
生存时间 (TTL) 决定了内容缓存的时长。拉取式 CDN 可以最大限度地减少 CDN 上的存储空间，但如果文件过期并在实际更改之前被拉取，则可能会造成冗余流量。

Sites with heavy traffic work well with pull CDNs, as traffic is spread out more evenly with only recently-requested content remaining on the CDN.
流量大的网站非常适合使用拉取式 CDN，因为流量会更均匀地分散，CDN 上只会保留最近请求的内容。

Disadvantage(s): CDN缺点：CDN

  • CDN costs could be significant depending on traffic, although this should be weighed with additional costs you would incur not using a CDN.
    CDN 的费用可能很大，具体取决于流量，不过这应该与不使用 CDN 而产生的额外费用进行权衡。
  • Content might be stale if it is updated before the TTL expires it.
    如果内容在 TTL 过期之前更新，则内容可能已过时。
  • CDNs require changing URLs for static content to point to the CDN.
    CDN 需要更改静态内容的 URL，使其指向 CDN。

Source: Scalable system design patterns

Load balancers distribute incoming client requests to computing resources such as application servers and databases. In each case, the load balancer returns the response from the computing resource to the appropriate client. Load balancers are effective at:
负载均衡器将传入的客户端请求分发到计算资源，例如应用服务器和数据库。在每个应用中，负载均衡器都会将计算资源的响应返回给相应的客户端。负载均衡器的优势在于：

  • Preventing requests from going to unhealthy servers
    防止请求发送到不健康的服务器
  • Preventing overloading resources

  • Helping to eliminate a single point of failure

Load balancers can be implemented with hardware (expensive) or with software such as HAProxy.

为了防止故障，通常会设置多个负载均衡器，采用 主备 模式或 主主 模式。

负载均衡器可以根据各种指标来路由流量，包括：

  • Least loaded

Layer 4 load balancing第四层负载均衡

Layer 4 load balancers look at info at the transport layer to decide how to distribute requests. Generally, this involves the source, destination IP addresses, and ports in the header, but not the contents of the packet. Layer 4 load balancers forward network packets to and from the upstream server, performing Network Address Translation (NAT).
第四层负载均衡器会查看 传输层 的信息来决定如何分配请求。通常，这包括数据包头部中的源 IP 地址、目标 IP 地址和端口，但不包括数据包的内容。第四层负载均衡器会将网络数据包转发到上游服务器并从上游服务器接收数据包，执行 网络地址转换 (NAT) 。

Layer 7 load balancing第七层负载均衡

Layer 7 load balancers look at the application layer to decide how to distribute requests. This can involve contents of the header, message, and cookies. Layer 7 load balancers terminate network traffic, reads the message, makes a load-balancing decision, then opens a connection to the selected server.
第七层负载均衡器会查看 应用层 ，以决定如何分配请求。这可能涉及请求头、消息和 Cookie 的内容。第七层负载均衡器会终止网络流量，读取消息，做出负载均衡决策，然后与选定的服务器建立连接。
For example, a layer 7 load balancer can direct video traffic to servers that host videos while directing more sensitive user billing traffic to security-hardened servers.
例如，第 7 层负载均衡器可以将视频流量定向到托管视频的服务器，同时将更敏感的用户计费流量定向到安全加固的服务器。

At the cost of flexibility, layer 4 load balancing requires less time and computing resources than Layer 7, although the performance impact can be minimal on modern commodity hardware.
虽然牺牲了灵活性，但第 4 层负载均衡所需的时间和计算资源比第 7 层少，尽管在现代通用硬件上性能影响可能很小。

It is also easier to hire for talent working on commodity hardware than it is for specialized enterprise systems.
负载均衡器还可以帮助实现横向扩展，从而提升性能和可用性。使用通用机器进行横向扩展比在更昂贵的硬件上扩展单个服务器（称为 纵向扩展 ）更具成本效益，并且可用性更高。此外，与专用企业系统相比，为通用硬件招聘人才也更容易。

  • Scaling horizontally introduces complexity and involves cloning servers
    水平扩展会引入复杂性，并且涉及服务器克隆。
    • Servers should be stateless: they should not contain any user-related data like sessions or profile pictures
      服务器应该是无状态的：它们不应该包含任何与用户相关的数据，例如会话或个人资料图片。
      • Sessions can be stored in a centralized data store such as a database (SQL, NoSQL) or a persistent cache (Redis, Memcached)

  • Downstream servers such as caches and databases need to handle more simultaneous connections as upstream servers scale out
    随着上游服务器横向扩展，下游服务器（例如缓存和数据库）需要处理更多并发连接。

Disadvantage(s): load balancer缺点：负载均衡器

Relational database management system (RDBMS)关系数据库管理系统（RDBMS）

ACID is a set of properties of relational database transactions.

  • Atomicity - Each transaction is all or nothing
    原子性 ——每笔交易要么全部成功，要么全部失败。
  • Consistency - Any transaction will bring the database from one valid state to another
    一致性 ——任何事务都会将数据库从一个有效状态带到另一个有效状态。
  • Isolation - Executing transactions concurrently has the same results as if the transactions were executed serially
    隔离性 ——并发执行事务与串行执行事务的结果相同。
  • Durability - Once a transaction has been committed, it will remain so

If the master goes offline, the system can continue to operate in read-only mode until a slave is promoted to a master or a new master is provisioned.
如果主节点离线，系统可以继续以只读模式运行，直到从节点被提升为主节点或配置新的主节点为止。

Federation (or functional partitioning) splits up databases by function. For example, instead of a single, monolithic database, you could have three databases: forums, users, and products, resulting in less read and write traffic to each database and therefore less replication lag. Smaller databases result in more data that can fit in memory, which in turn results in more cache hits due to improved cache locality.
联合（或功能分区）按功能拆分数据库。例如，与其使用单一的单体数据库，不如使用三个数据库： 论坛 、 用户 和 产品 ，这样可以减少每个数据库的读写流量，从而降低复制延迟。更小的数据库意味着更多的数据可以加载到内存中，进而由于缓存局部性的提高而增加缓存命中率。

Sharding distributes data across different databases such that each database can only manage a subset of the data. Taking a users database as an example, as the number of users increases, more shards are added to the cluster.
分片技术将数据分布在不同的数据库中，使得每个数据库只能管理一部分数据。以用户数据库为例，随着用户数量的增加，集群中会添加更多的分片。

Similar to the advantages of federation, sharding results in less read and write traffic, less replication, and more cache hits. Index size is also reduced, which generally improves performance with faster queries.
与 联邦 的优势类似，分片可以减少读写流量、减少数据复制，并提高缓存命中率。索引大小也会减小，这通常可以提高性能，加快查询速度。
If one shard goes down, the other shards are still operational, although you'll want to add some form of replication to avoid data loss. Like federation, there is no single central master serializing writes, allowing you to write in parallel with increased throughput.
如果一个分片宕机，其他分片仍然可以正常运行，但为了避免数据丢失，最好添加某种形式的数据复制机制。与联邦机制类似，这种架构没有单一的中央主节点来串行执行写入操作，因此可以并行写入，从而提高吞吐量。

Common ways to shard a table of users is either through the user's last name initial or the user's geographic location.
对用户表进行分片的常见方法是按用户姓氏的首字母或用户的地理位置进行分片。

Denormalization非规范化

Denormalization attempts to improve read performance at the expense of some write performance. Redundant copies of the data are written in multiple tables to avoid expensive joins. Some RDBMS such as PostgreSQL and Oracle support materialized views which handle the work of storing redundant information and keeping redundant copies consistent.
反规范化旨在以牺牲部分写入性能为代价来提升读取性能。它将数据的冗余副本写入多个表中，以避免代价高昂的连接操作。一些关系型数据库管理系统（RDBMS），例如 PostgreSQL 和 Oracle，支持 物化视图 ，后者负责存储冗余信息并保持冗余副本的一致性。

Once data becomes distributed with techniques such as federation and sharding, managing joins across data centers further increases complexity. Denormalization might circumvent the need for such complex joins.
一旦数据通过 联邦 和 分片 等技术实现分布式存储，跨数据中心管理连接操作的复杂性就会进一步增加。反规范化或许可以避免这种复杂的连接操作。

In most systems, reads can heavily outnumber writes 100:1 or even 1000:1. A read resulting in a complex database join can be very expensive, spending a significant amount of time on disk operations.
在大多数系统中，读取操作的数量可能远远超过写入操作，比例可达 100:1 甚至 1000:1。一次复杂的数据库连接操作可能会非常耗时，因为磁盘操作会消耗大量时间。

NoSQL

NoSQL is a collection of data items represented in a key-value store, document store, wide column store, or a graph database. Data is denormalized, and joins are generally done in the application code. Most NoSQL stores lack true ACID transactions and favor eventual consistency.
NoSQL 是一种数据集合，数据项以 键值存储 、 文档存储 、 宽列存储 或 图数据库的 形式呈现。数据是非规范化的，连接操作通常在应用程序代码中完成。大多数 NoSQL 存储缺乏真正的 ACID 事务，并且倾向于 最终一致性 。

BASE 通常用于描述 NoSQL 数据库的特性。与 CAP 定理 相比，BASE 更注重可用性而非一致性。

  • Soft state - the state of the system may change over time, even without input.
    软状态 ——即使没有输入，系统状态也可能随时间发生变化。
  • Eventual consistency - the system will become consistent over a period of time, given that the system doesn't receive input during that period.
    最终一致性 ——如果系统在一段时间内没有收到输入，那么系统将在一段时间内趋于一致。

Cache-aside缓存旁


Source: From cache to in-memory data grid
来源：从缓存到内存数据网格

The application is responsible for reading and writing from storage. The cache does not interact with storage directly. The application does the following:
应用程序负责从存储器读取和写入数据。缓存不直接与存储器交互。应用程序执行以下操作：

  • Look for entry in cache, resulting in a cache miss
    查找缓存条目，导致缓存未命中
  • Load entry from the database
    从数据库加载条目
  • Add entry to cache
    向缓存添加条目
  • Return entry
    返回条目
def get_user(self, user_id):
    user = cache.get("user.{0}", user_id)
    if user is None:
        user = db.query("SELECT * FROM users WHERE user_id = {0}", user_id)
        if user is not None:
            key = "user.{0}".format(user_id)
            cache.set(key, json.dumps(user))
    return user

Memcached is generally used in this manner.
Memcached 通常就是这样使用的。

Subsequent reads of data added to cache are fast. Cache-aside is also referred to as lazy loading. Only requested data is cached, which avoids filling up the cache with data that isn't requested.
后续读取缓存中的数据速度很快。缓存旁路技术也称为延迟加载。只有请求的数据才会被缓存，这样可以避免缓存中填充未被请求的数据。

Disadvantage(s): cache-aside缺点：缓存旁
  • Each cache miss results in three trips, which can cause a noticeable delay.
    每次缓存未命中都会导致三次往返，这可能会造成明显的延误。
  • Data can become stale if it is updated in the database. This issue is mitigated by setting a time-to-live (TTL) which forces an update of the cache entry, or by using write-through.
    如果数据库中的数据被更新，则数据可能会过期。可以通过设置生存时间 (TTL) 来缓解此问题，TTL 会强制更新缓存条目，或者使用直写方式。
  • When a node fails, it is replaced by a new, empty node, increasing latency.
    当一个节点发生故障时，它会被一个新的空节点替换，从而增加延迟。

Write-through通写式

The application uses the cache as the main data store, reading and writing data to it, while the cache is responsible for reading and writing to the database:
该应用程序使用缓存作为主要数据存储，对缓存进行数据读写操作，而缓存则负责对数据库进行数据读写操作：

  • Application adds/updates entry in cache
    应用程序在缓存中添加/更新条目
  • Cache synchronously writes entry to data store
    缓存同步地将条目写入数据存储
  • Return
    返回

应用程序代码：

set_user(12345, {"foo":"bar"})

Cache code:
缓存代码：

def set_user(user_id, values):
    user = db.query("UPDATE Users WHERE id = {0}", user_id, values)
    cache.set(user_id, user)

Write-through is a slow overall operation due to the write operation, but subsequent reads of just written data are fast. Users are generally more tolerant of latency when updating data than reading data. Data in the cache is not stale.
由于写入操作本身较慢，因此直写式操作整体速度较慢，但后续读取已写入的数据速度很快。用户通常对更新数据的延迟容忍度高于读取数据。缓存中的数据不会过期。

Disadvantage(s): write through缺点：通读
  • When a new node is created due to failure or scaling, the new node will not cache entries until the entry is updated in the database. Cache-aside in conjunction with write through can mitigate this issue.
    当因故障或扩容而创建新节点时，新节点不会缓存条目，直到数据库中的条目被更新。缓存旁路（Cache-side）结合直写（Write-Through）可以缓解此问题。
  • Most data written might never be read, which can be minimized with a TTL.
    写入的大部分数据可能永远不会被读取，而使用 TTL 可以最大限度地减少这种情况。

  • Asynchronously write entry to the data store, improving write performance

Message queues receive, hold, and deliver messages. If an operation is too slow to perform inline, you can use a message queue with the following workflow:

  • An application publishes a job to the queue, then notifies the user of job status
    应用程序将作业发布到队列中，然后通知用户作业状态
  • A worker picks up the job from the queue, processes it, then signals the job is complete

HTTP 是一种用于在客户端和服务器之间编码和传输数据的方法。它是一种请求/响应协议：客户端发出请求，服务器发出包含相关内容和请求完成状态信息的响应。
HTTP is self-contained, allowing requests and responses to flow through many intermediate routers and servers that perform load balancing, caching, encryption, and compression.
HTTP 是自包含的，允许请求和响应流经许多中间路由器和服务器，这些路由器和服务器执行负载均衡、缓存、加密和压缩。

Transmission control protocol (TCP)传输控制协议（TCP）


Source: How to make a multiplayer game
来源：如何制作多人游戏

TCP is a connection-oriented protocol over an IP network. Connection is established and terminated using a handshake. All packets sent are guaranteed to reach the destination in the original order and without corruption through:
TCP 是一种基于 IP 网络的 面向连接的协议。连接通过 握手 建立和终止。所有发送的数据包都能保证按原始顺序无损地到达目的地，其机制如下：

  • Sequence numbers and checksum fields for each packet
    每个数据包的序列号和 校验和字段
  • Acknowledgement packets and automatic retransmission
    确认 包和自动重传

If the sender does not receive a correct response, it will resend the packets. If there are multiple timeouts, the connection is dropped. TCP also implements flow control and congestion control. These guarantees cause delays and generally result in less efficient transmission than UDP.
如果发送方没有收到正确的响应，它会重新发送数据包。如果出现多次超时，连接将被断开。TCP 还实现了 流量控制 和 拥塞控制 。这些机制会导致延迟，并且通常比 UDP 的传输效率低。

To ensure high throughput, web servers can keep a large number of TCP connections open, resulting in high memory usage. It can be expensive to have a large number of open connections between web server threads and say, a memcached server. Connection pooling can help in addition to switching to UDP where applicable.
为了确保高吞吐量，Web 服务器可以保持大量 TCP 连接打开，这会导致内存占用过高。在 Web 服务器线程和 memcached 服务器等对象之间保持大量打开的连接会消耗大量资源。除了在适用情况下切换到 UDP 协议外 ，连接池 也能有所帮助。

TCP is useful for applications that require high reliability but are less time critical. Some examples include web servers, database info, SMTP, FTP, and SSH.
TCP 适用于对可靠性要求高但对时间要求不高的应用。例如，Web 服务器、数据库信息、SMTP、FTP 和 SSH 等都使用 TCP 协议。

Use TCP over UDP when:
在以下情况下使用 TCP 而非 UDP：

  • You need all of the data to arrive intact
    你需要所有数据完好无损地到达。
  • You want to automatically make a best estimate use of the network throughput
    您希望自动对网络吞吐量进行最佳估算利用。

User datagram protocol (UDP)用户数据报协议（UDP）


Source: How to make a multiplayer game
来源：如何制作多人游戏

UDP is connectionless. Datagrams (analogous to packets) are guaranteed only at the datagram level. Datagrams might reach their destination out of order or not at all. UDP does not support congestion control.
UDP 是无连接的。数据报（类似于数据包）的质量保证仅限于数据报层面。数据报可能乱序到达目的地，甚至根本无法到达。UDP 不支持拥塞控制。
Without the guarantees that TCP support, UDP is generally more efficient.
如果没有 TCP 支持的保证，UDP 通常效率更高。

UDP can broadcast, sending datagrams to all devices on the subnet. This is useful with DHCP because the client has not yet received an IP address, thus preventing a way for TCP to stream without the IP address.
UDP 可以广播数据报，将数据报发送到子网上的所有设备。这在 DHCP 环境下非常有用，因为客户端尚未收到 IP 地址，从而阻止了 TCP 在没有 IP 地址的情况下进行数据流传输。

UDP is less reliable but works well in real time use cases such as VoIP, video chat, streaming, and realtime multiplayer games.
UDP 的可靠性较低，但在 VoIP、视频聊天、流媒体和实时多人游戏等实时应用场景中表现良好。

Use UDP over TCP when:
在以下情况下使用 UDP 而非 TCP：

  • You need the lowest latency
    你需要最低的延迟。
  • Late data is worse than loss of data
    数据延迟比数据丢失更糟糕。
  • You want to implement your own error correction
    你想实现自己的纠错机制。

Remote procedure call (RPC)远程过程调用（RPC）


Source: Crack the system design interview
来源：破解系统设计面试

In an RPC, a client causes a procedure to execute on a different address space, usually a remote server. The procedure is coded as if it were a local procedure call, abstracting away the details of how to communicate with the server from the client program.
在远程过程调用（RPC）中，客户端会触发一个过程在不同的地址空间（通常是远程服务器）上执行。该过程的编码方式与本地过程调用相同，从而将如何与服务器通信的细节对客户端程序进行了抽象。
Remote calls are usually slower and less reliable than local calls so it is helpful to distinguish RPC calls from local calls.
远程调用通常比本地调用速度慢、可靠性低，因此区分 RPC 调用和本地调用很有帮助。
Popular RPC frameworks include Protobuf, Thrift, and Avro.
流行的 RPC 框架包括 Protobuf 、 Thrift 和 Avro 。

RPC is a request-response protocol:
RPC 是一种请求-响应协议：

  • Client program - Calls the client stub procedure. The parameters are pushed onto the stack like a local procedure call.
    客户端程序 ——调用客户端存根过程。参数像本地过程调用一样被压入堆栈。
  • Client stub procedure - Marshals (packs) procedure id and arguments into a request message.
    客户端存根过程 - 将过程 ID 和参数打包到请求消息中。
  • Client communication module - OS sends the message from the client to the server.
    客户端通信模块 - 操作系统将消息从客户端发送到服务器。
  • Server communication module - OS passes the incoming packets to the server stub procedure.
    服务器通信模块 - 操作系统将传入的数据包传递给服务器存根过程。
  • Server stub procedure - Unmarshalls the results, calls the server procedure matching the procedure id and passes the given arguments.
    服务器存根过程 - 反序列化结果，调用与过程 ID 匹配的服务器过程，并传递给定的参数。
  • The server response repeats the steps above in reverse order.
    服务器响应会按相反的顺序重复上述步骤。

Sample RPC calls:
RPC 调用示例：

GET /someoperation?data=anId

POST /anotheroperation
{
  "data":"anId";
  "anotherdata": "another value"
}

RPC is focused on exposing behaviors. RPCs are often used for performance reasons with internal communications, as you can hand-craft native calls to better fit your use cases.
RPC 的重点在于暴露行为。出于性能考虑，RPC 通常用于内部通信，因为您可以手动编写原生调用以更好地满足您的使用场景。

Choose a native library (aka SDK) when:
在以下情况下选择原生库（也称为 SDK）：

  • You know your target platform.
    您了解您的目标平台。
  • You want to control how your "logic" is accessed.
    你想控制别人如何访问你的“逻辑”。
  • You want to control how error control happens off your library.
    你想控制库之外的错误处理方式。
  • Performance and end user experience is your primary concern.
    性能和最终用户体验是您的首要考虑因素。

HTTP APIs following REST tend to be used more often for public APIs.
遵循 REST 规范的 HTTP API 通常更常用于公共 API。

Disadvantage(s): RPC缺点：RPC

  • RPC clients become tightly coupled to the service implementation.
    RPC 客户端与服务实现紧密耦合。
  • A new API must be defined for every new operation or use case.
    每新增一项操作或用例，都需要定义一个新的 API。
  • It can be difficult to debug RPC.
    调试 RPC 可能很困难。
  • You might not be able to leverage existing technologies out of the box. For example, it might require additional effort to ensure RPC calls are properly cached on caching servers such as Squid.
    你可能无法直接利用现有技术。例如，可能需要额外努力来确保 RPC 调用在 Squid 等缓存服务器上 得到正确缓存 。

Representational state transfer (REST)表述性状态转移（REST）

REST is an architectural style enforcing a client/server model where the client acts on a set of resources managed by the server. The server provides a representation of resources and actions that can either manipulate or get a new representation of resources.
REST 是一种架构风格，它采用客户端/服务器模型，其中客户端操作由服务器管理的一组资源。服务器提供资源的表示形式以及可以操作资源或获取资源新表示形式的操作。
All communication must be stateless and cacheable.
所有通信都必须是无状态的且可缓存的。

There are four qualities of a RESTful interface:
RESTful 接口具有四个特点：

  • Identify resources (URI in HTTP) - use the same URI regardless of any operation.
    标识资源（HTTP 中的 URI） - 无论进行任何操作，都使用相同的 URI。
  • Change with representations (Verbs in HTTP) - use verbs, headers, and body.
    使用表示形式（HTTP 中的动词）进行更改 - 使用动词、标头和正文。
  • Self-descriptive error message (status response in HTTP) - Use status codes, don't reinvent the wheel.
    自描述性错误消息（HTTP 中的状态响应） - 使用状态代码，不要重复造轮子。
  • HATEOAS (HTML interface for HTTP) - your web service should be fully accessible in a browser.
    HATEOAS （HTTP 的 HTML 接口） ——您的 Web 服务应该可以在浏览器中完全访问。

Sample REST calls:
REST 调用示例：

GET /someresources/anId

PUT /someresources/anId
{"anotherdata": "another value"}

REST is focused on exposing data. It minimizes the coupling between client/server and is often used for public HTTP APIs. REST uses a more generic and uniform method of exposing resources through URIs, representation through headers, and actions through verbs such as GET, POST, PUT, DELETE, and PATCH. Being stateless, REST is great for horizontal scaling and partitioning.
REST 专注于数据暴露。它最大限度地降低了客户端/服务器之间的耦合度，常用于公共 HTTP API。REST 使用更通用、更统一的方法，通过 URI 暴露资源， 通过请求头表示数据 ，并通过 GET、POST、PUT、DELETE 和 PATCH 等动词执行操作。由于 REST 是无状态的，因此非常适合横向扩展和分区。

Disadvantage(s): REST缺点：休息

  • With REST being focused on exposing data, it might not be a good fit if resources are not naturally organized or accessed in a simple hierarchy. For example, returning all updated records from the past hour matching a particular set of events is not easily expressed as a path.
    由于 REST 侧重于暴露数据，因此如果资源没有以简单的层级结构自然组织或访问，它可能就不太适用。例如，返回过去一小时内所有符合特定事件集的更新记录，很难用路径来表示。
    With REST, it is likely to be implemented with a combination of URI path, query parameters, and possibly the request body.
    使用 REST 时，很可能是通过 URI 路径、查询参数以及可能的请求正文的组合来实现的。
  • REST typically relies on a few verbs (GET, POST, PUT, DELETE, and PATCH) which sometimes doesn't fit your use case. For example, moving expired documents to the archive folder might not cleanly fit within these verbs.
    REST 通常依赖于几个动词（GET、POST、PUT、DELETE 和 PATCH），但有时这些动词并不完全符合您的使用场景。例如，将过期文档移动到归档文件夹可能并不适合使用这些动词。
  • Fetching complicated resources with nested hierarchies requires multiple round trips between the client and server to render single views, e.g. fetching content of a blog entry and the comments on that entry.
    获取具有嵌套层次结构的复杂资源需要客户端和服务器之间多次往返才能渲染单个视图，例如获取博客文章的内容和该文章的评论。
    For mobile applications operating in variable network conditions, these multiple roundtrips are highly undesirable.
    对于在网络状况不稳定的情况下运行的移动应用程序而言，这种多次往返是非常不理想的。
  • Over time, more fields might be added to an API response and older clients will receive all new data fields, even those that they do not need, as a result, it bloats the payload size and leads to larger latencies.
    随着时间的推移，API 响应中可能会添加更多字段，而旧客户端将收到所有新的数据字段，即使是它们不需要的字段，这会导致有效负载大小膨胀，从而导致更大的延迟。
